# ADR 0068 — Authorization hardening: tenant.admin implication, self-service rules, X-Tenant-Id scoping, must-change enforcement, refresh grace

**Status:** Accepted
**Date:** 2026-11-19
**Supersedes (in part):** [ADR 0036](0036-permission-model.md) (resolution rule), [ADR 0053](0053-must-change-password-and-account-lockout.md) (deferred work #1), [ADR 0039](0039-per-request-scope-selection.md) (no-header operator scope)
**Builds on:** [ADR 0044](0044-enumeration-safety-404-on-no-access.md), [ADR 0045](0045-scoped-jwt-impersonation-act-claim.md), [ADR 0055](0055-permission-elevation-approval-workflow.md)

## Context

A security audit of the identity module and the BFF contract found a family of authorization defects sharing one root: most mutating identity routes were gated by authentication only (`auth(...)`), so any authenticated tenant member could call them.

- **Authentication-only mutations.** Any member could assign roles, override permissions, create users and edit roles, including granting themselves `tenant.admin`. Role assignment was equivalent to `tenant.admin` because nothing bounded what a caller could confer.
- **`tenant.admin` did not mean what the ADRs say it means.** ADR 0061 amendment 1, ADR 0045 and the seed godoc treat it as full operational authority inside the tenant, but the resolution rule did not satisfy catalogue permissions from it uniformly, and its reach into other modules was undefined.
- **`X-Tenant-Id` (ADR 0039).** The header was not honoured as the ADR specifies: the ADR says it is IGNORED for everyone but slug-anchored platform operators, and malformed or unknown values need defined errors.
- **`must_change_password` (ADR 0053 deferred work #1)** was a login-response flag only; nothing enforced it on the API.
- **Impersonation tokens (ADR 0045)** were accepted on self-service routes and by `RequirePlatform`, were not checked against a live session, and the audience/`act` agreement was not enforced.
- **Refresh rotation** had no grace window, so a lost response (network drop, double tab) revoked the whole family as reuse.
- **Rate limiting and enumeration.** The limiter keyed on the raw peer address and had no per-route tightening; a 423 on login revealed that an account exists (ten probes against an unknown email never lock); password-reset response time was a timing oracle.
- **Password policy** stored per tenant was not enforced on create, change or reset.
- **Tenant registration** was anonymous although ADR 0053 states there is no public sign-up surface.

## Decision

**D1 – what `tenant.admin` grants.** `tenant.admin` satisfies every catalogue permission, including other modules' (crm, inventory, orders, tasks, dispatch, notifications, marketplace, lead-credits read), but only in the caller's own tenant (claims `tenant_id` must equal the effective tenant). It never satisfies platform-reserved permissions: `platform.tenants.*`, `platform.users.*`, `platform.roles.*`, `platform.unverified_contacts.manage`, `platform.lead_credits.topup`, `identity.tenants.{suspend,activate,delete}`, `identity.users.anonymise`. Grounds: ADR 0061 amendment 1 (CompanyOwner short-circuits via `Meta.TenantAdmin`), the seed godoc ("full operational authority"), ADR 0045 (operators get the full CompanyOwner permission set in-session; the impersonation token carries `["tenant.admin"]`). Re-seeding was rejected: ADR 0036 Alternative 5 argues against enumerating permissions on a role, and stored roles would need a data migration whenever the catalogue grows.

**D2 – platform equivalents on the unified surface.** On `/v1/users`, `/v1/roles`, `/v1/tenants` (ADR 0039 Context), a slug-anchored, non-impersonation platform operator also satisfies `identity.users|roles|tenants.*` through the `platform.*` catalogue entries (view to view|manage, mutations to manage, users.create to create|manage). This mirrors the .NET `PlatformTenant{User,Role,Management}Endpoints` gates.

**D3 – self-service rules.** `GET /users/{id}` and `PATCH /users/{id}/profile` pass for self (path id equals the caller's `membership_id`) or with `users.view` / `users.update`. Roles, permission overrides, deactivate/reactivate and manager changes are denied on self for everyone except super users, preventing both self-escalation and owner self-lockout.

**D4 – no grant beyond your own authority.** A caller may only confer permissions they themselves satisfy: role assignment checks the role's permission set, and only super users may assign `is_super_admin` roles. Role permission grant/replace and user override grants are checked the same way. Grounds: ADR 0036 closed set and ADR 0055 "privilege plane".

**D5 – permission-request routes stay as they are.** List/get/submit/approve/deny/cancel remain authentication-only with handler-inline checks, which is the design of ADR 0055 section 8 (list is scoped to the caller's own membership; get collapses to 404). They are on the arch-test allowlist.

**D6 – tenant registration is operator-only.** `POST /api/v1/tenants` is not self-service (ADR 0053: B2B, operator-onboarded, no public sign-up surface). New gate: `RequirePlatform` plus `platform.tenants.create`, with its own rate limit.

**D6a – platform routes are authorised by permission, not by platform-tenant membership.** `is_platform` is minted from the tenant slug alone, so `RequirePlatform` / `IsPlatformOperator` prove membership of the platform tenant and nothing else. Every route registered through `authn.RequirePlatformGate` therefore names the permission that authorises it, evaluated by the one `authn.Satisfies` decision (D1): both anonymise routes `identity.users.anonymise`; tenant suspend / activate `identity.tenants.suspend` / `identity.tenants.activate`; mark-for-deletion, restore and `DELETE /platform/tenants/{id}` `identity.tenants.delete` (the catalogue has no restore permission); platform person mutations `platform.users.manage`; impersonation-session create / list / end `platform.impersonation.manage` (platform-reserved; a session mints a `tenant.admin` token for any tenant, so it is not folded into `platform.tenants.manage`); cross-tenant reads `platform.tenants.view` / `platform.users.view` (omni-search needs either, and each category needs its own: `persons` needs `platform.users.view`, `tenants` needs `platform.tenants.view`; with no `include` it returns the authorised subset, and an explicitly requested category the caller may not see is 403 `search_category_forbidden`). `tenant.admin` never implies any of them (they are platform-reserved), and the arch gate no longer counts `RequirePlatform` alone as authorisation, GETs included.

**D7 – `X-Tenant-Id` (ADR 0039 decision tree).** The header is honoured only for slug-anchored, non-impersonation `is_platform` callers; for everyone else it is ignored, with a debug log line. A malformed value yields 400 `invalid_tenant_scope`; an unknown or deleted tenant yields 404 `tenant_scope_not_found`. On `/tenants/{tenantId}` routes the path wins, and a header that differs from the path yields 400 `tenant_scope_conflict`. Audit is one structured `slog` INFO line per scoped request with ADR 0039's fields (`scope_mode`, `effective_tenant_id`, `caller_tenant_id`); ADR 0056 defers HTTP-side audit rows. Capabilities ignores the header (claims only). Minimum-faithful deviation (owner ruling): without the header, operators act in their own tenant — no TxScopePlatform reads and no `ambiguous_scope` 403. Because no-header is never cross-tenant, ADR 0039 Alternative 4's blast-radius hazard cannot occur.

**D7 amendment (per-route scope policy).** Every registered route has exactly one scope policy, declared in exactly one place, and a route marker always beats the central table:

| Policy | Header | Declared by |
|---|---|---|
| IGNORE | not validated, not looked up, not audited; effective tenant = the caller's own | the central table (`scope_policy.go`): `/api/v1/auth/*`, `/api/v1/notifications*` (the caller's own inbox), `/api/v1/platform/*`, `POST /tenants`, `GET /tenants`, `GET /tenants/by-slug/{slug}`, `GET /search` — only for a route with no marker |
| REJECT | a foreign tenant is 403 `tenant_scope_not_supported` | `authn.RejectTenantScope` (permission requests, lead purchase) |
| path-tenant | the path wins; a differing header is 400 `tenant_scope_conflict`; a header equal to the path selects nothing (no scope authority check, no lookup: the route's own permission gate decides and attributes); writable by definition; exempt from the inactive-tenant 409 | `authn.RequireTenantPermission`, `TenantScopeLifecycle`, `TenantScopePathOnly` (hard delete never applies the header) |
| honour | selects the effective tenant; the permission gate is evaluated there | the default; `authn.HonourTenantScope` where the route sits inside an ignored group (lead-credit balance) |

*Scope authority.* Honouring a foreign tenant needs more than platform-tenant membership: the caller must be a super user or a slug-anchored operator holding `platform.tenants.view` (`authn.CanActAcrossTenants`). Anyone else naming a foreign tenant gets 403 `tenant_scope_forbidden`, decided before any tenant lookup and identical for existing, unknown and suspended tenants (no enumeration oracle). An ordinary tenant user's header stays silently ignored.

*Read-only by default.* On an honoured route a non-read request that selects a foreign tenant is 403 `tenant_scope_read_only` unless the route opts in with `authn.TenantScopeWritable`. The writable set is the identity writes the operator scope tree performs (create user, user profile, deactivate, reactivate, role assign / revoke, permission overrides, manager set / clear, anonymise, role create / update / delete, role permissions replace / grant / revoke, role parent) and is pinned, route by route, by `TestArch_ImpersonationToken_RefusedExactlyWhereTheListSays` and `TestArch_MustChangePassword_BlocksEveryRouteButThePinnedAllowlist` (`session_policy_arch_test.go`) serve every registered route through the real `AddRoutes`: the first pins the impersonation refusal list and the two exempt tenant-plane reads exactly, requires every platform-anchored route to be refused and every authenticated `/api/v1/auth/` route, whatever its gate, to be in exactly one of two pinned sets (refused / open); the second proves a flagged token is blocked everywhere but the two-route allowlist. `TestArch_NoProductionCodeImportsATestHelperPackage` keeps `identitytest` and the other `*test` helpers out of production code. Not covered: a route registered outside `AddRoutes`, and files carrying the `integration` build tag.

`TestArch_EveryRouteIsScopeClassified`. crm, orders, tasks, dispatch and inventory mutations are therefore never accepted under a foreign header, so the operator's platform-tenant membership id is never stamped into another tenant's rows; no nullable or system actor is introduced.

*Inactive tenants.* A write into a suspended or pending-deletion tenant through the header on a non-path route is 409 `tenant_not_active`; reads are allowed. Path-tenant routes (`PATCH /tenants/{id}/...`, lifecycle) are exempt because the path is authoritative: the same request succeeds with and without the header.

*Attribution.* An anchored operator who acts outside the token's tenant, or through a platform-gated route, carries the act claim (ADR 0056) on every such request, so outbox and audit rows are durably attributed: `act_reason` `tenant-via-header` when the header selected the tenant, `tenant-via-path` when a `RequireTenantPermission` route re-bound the URL tenant, and `platform-route` when neither applied (`authn.RequirePlatformGate` stamps it, once, as its innermost wrapper, covering header-less lifecycle calls, hard delete, platform person operations, and the platform module's writes; a claim already on the request is never overwritten). The scope decision is applied once per request even when auth gates nest (one lookup, one INFO line).

*Cross-tenant lookups.* Tenant lookups by slug (`GET /tenants/by-slug/{slug}`, `GET /tenants?slug=`) and the own-caseload narrowing in crm and tasks use the same predicate (`authn.CanActAcrossTenants`), not membership, and both lookups are gated by `RequireAnyPermission(identity.tenants.view, platform.tenants.view)` (a zero-permission member is refused with 403; they are no longer authentication-only); the per-module `tenantFromContext` copies are gone and handlers read the tenant through `authn.EffectiveTenantID` (the other modules) or `tenancy.FromContext` (identity handlers, which is the same value: the auth gate binds the effective tenant on the context), and `EffectiveTenantID` fails closed.

**D8 – `must_change_password` enforcement (as built).** It is a JWT claim (`must_change_password`, omitted when false, so tokens minted before the claim read as un-flagged), as ADR 0053 deferred work #1 specifies. Login and refresh mint it from the stored Person (`command/login.go`, `command/refresh.go`) and return it as `must_change_password` in their response; capabilities returns it from the token. ONE place enforces it: `RequireFreshStamp` (`authn/security_stamp.go`; every `Require*` factory is built on it), which every authenticated route passes through, answers 403 `password_change_required` (no `WWW-Authenticate`: it is not a session problem) for a flagged token on every route except the exactly-pinned `authn.PendingPasswordChangeAllowlist`: `POST /api/v1/auth/change-password` and `GET /api/v1/auth/me/capabilities`, compared against the matched route pattern (`r.Pattern`), so a new route, or a request with no pattern, is blocked by default. Login, refresh, logout and the emailed-token flows are anonymous and never see the check (`anonymousAPIRoutes`). `TestArch_MustChangePassword_BlocksEveryRouteButThePinnedAllowlist` serves every scanned route with a flagged token and proves each one is blocked, except the allowlist and the pinned anonymous set. The claim cannot go stale: changing the password rotates the stamp and kills the token, and revokes every refresh family of the person in the same unit of work (`ChangePassword` and `ConfirmPasswordReset` via `revokeAllFamilies`; the access token carries no family id, so the caller's own family is revoked too, and the BFF signs in again with the new password); the next LOGIN carries no flag. Refresh re-reads the family after reading the person and refuses a revoked one, and the family row is locked for update, so a rotation racing the change can neither mint a usable token nor write the revocation away. The outbox subscriber stays as an idempotent backstop. The flag is set by `RegisterTenant` (the first admin) and `CreateUser` (`NewWithMustChangePassword`) and cleared by `ChangePassword` and `ConfirmPasswordReset`; no operator-reset command exists. Impersonation: the flag belongs to the person behind the token, the operator. The impersonation mint never copies it (the tenant user's flag is irrelevant to an operator acting in their tenant), and an operator who is flagged is blocked on every route, including the one that opens a session. So the plan's word "exempt" is not what is built: nothing is exempt; the impersonation token simply never carries the flag, while a flagged operator is blocked everywhere. **Recorded constraint:** any future "admin resets a member's password" command MUST set `must_change_password` and rotate the security stamp (and revoke the person's refresh families, as `ChangePassword` does); no such command exists today, and one that skipped them would hand the admin a standing credential.

**D9 – impersonation tokens (ADR 0045 closed-set audience).** Self-service identity routes (change-password, email change, sessions, `/me/activity`, permission-request mutations) return 403 `impersonation_not_allowed`. `RequirePlatform` rejects them explicitly. `aud=leadkart-impersonation` must agree with the presence of `act`, otherwise 401. The token is honoured only while its session exists (ADR 0045 step 7 bounds post-session access to 10 minutes, but tokens live up to 4 hours, so liveness is checked). Their reach comes from D1.

**D10 – refresh grace window.** A just-rotated token re-presented within `Refresh.GraceWindow` (default 30 s), while its direct successor is still the unconsumed chain head, receives the same successor again: no state change, no event. The successor is derived deterministically — HMAC-SHA256 with a key derived by HKDF from the JWT signing key, over family id and presented plaintext — so the server never stores plaintext and no schema change is needed. Outside the window, or once the successor has been used, presenting the old token is reuse and the family is revoked (RFC 9700 rotation; Auth0 reuse interval / Okta grace period canon).

**D11 – rate limiting stays in memory (ADR 0030 defers Redis).** Add a trusted-proxy client-IP keyer reading `X-Forwarded-For` only from trusted CIDRs, walking right-to-left and taking the first untrusted hop. Add configurable tighter per-route limits for login, refresh, request-password-reset, reset-password, confirm-email-change and tenant registration. The idempotency caller scope uses the same client IP.

**D12 – enumeration.** ADR 0053's argument that "the attacker already knew" is wrong: ten probes against an unknown email never lock, so a 423 reveals the account exists. Every no-account branch (unknown email, inactive, anonymised) runs a phantom lockout counter with the same thresholds, keeping ADR 0053's 423 UX and restoring ADR 0044's non-disclosure. The locked branch runs a dummy argon2 verify and still never verifies the real password. Request-password-reset has a fixed 300 ms response floor.

**D13 – password policy.** The stored tenant policy is enforced on create-user (target tenant), change-password (caller's tenant) and reset (active membership's tenant, else default). Registration uses `DefaultPasswordPolicy`. Rule codes: `min_length`, `requires_uppercase`, `requires_lowercase`, `requires_digit`, `requires_symbol` (a symbol is `unicode.IsPunct||IsSymbol`; spaces do not count). Response: 422 `password_policy_violation` with `errors{<field>:[rules]}`.

**D14 – membership writers, the acting member and cross-tenant ownership (hierarchy round 4; extends ADR 0069).** (a) *One writer at a time per membership.* `MembershipRepository.UpdateByID` loads the row `FOR NO KEY UPDATE` (and `PersonRepository.UpdateByID` the person row): the aggregate is persisted whole, so an unlocked load let a profile edit (allowed for the member themself) write a stale role set, status or owner count back over a committed authority change. Lock order is tenant advisory lock, membership row, person row; the multi-row writers all hold the advisory lock. (b) *The actor is re-read.* `authorityWriter.locked` loads the acting member inside the locked transaction and the policy decides with the token's actor narrowed by it (`Actor.NarrowedBy`: the more junior rank, the intersection of permissions); a missing or inactive member is `403 forbidden`; super users, impersonation sessions and operators under the cross-tenant exemption are not re-read. (c) *Authority changes end the affected session's old token, not the session.* A role assigned or revoked, overrides replaced, a deactivation or reactivation and an approved permission request rotate the target person's security stamp in the same transaction (`SecurityStampRotated`, evicted from the stamp cache by the existing subscriber, no family revocation): the next request answers `401 stale_token` + `WWW-Authenticate`, the BFF refreshes silently and the refreshed token carries the new rank and permissions; manager changes and profile edits rotate nothing. (d) *Ownership from outside needs `platform.tenants.ownership`.* The operator exemption (R3) no longer covers assigning or revoking Company Owner, conferring or removing `tenant.admin` (by role or override) or deactivating an owner; those need a super user or the platform-reserved `platform.tenants.ownership` (declared like `platform.impersonation.manage`; `403 ownership_authority_required`). The permission name is the controller's default pending the repository owner's confirmation. (e) Editing another member's profile is `MayActOn`; the manager command decides authority before eligibility; a person-level change takes the person row and re-reads the membership set it guarded; approving a name on the requester's revoked list is an un-revoke decided by `MayChangeOverrides` as well.

## Consequences

- Ordinary members (for example a Sales Executive) lose the tenant directory (`GET /users`, `GET /roles`) and tenant profile (`GET /tenants/{id}`) unless granted `*.view`.
- The web's operator console is the only tenant-registration caller; anonymous registration is gone.
- The default password policy requires all four character classes, contrary to NIST 800-63B composition guidance; the stored policy is enforced as is, and the owner may relax `DefaultPasswordPolicy` later.
- Permission resolution is a single decision (`Satisfies`) reused by every gate (`RequireTenantPermission`, `RequirePermissionOrSelf`, `DenySelfTarget`), so the rules above have one implementation.
- Existing roles need no data migration when the catalogue grows, because `tenant.admin` is an implication, not an enumeration (D1).
- **Rollout (D8).** Every person already flagged in a database (every first admin and every admin-created member who never changed the password) is forced to change it at the next login or refresh once this ships: the flag was stored but never enforced before. Change-password ends all of that person's sessions (D8), so they sign in again afterwards.

## Follow-up work (not in this ADR's scope)

- **No last-CompanyOwner protection.** The domain has no invariant preventing the last owner being deactivated by a `users.deactivate` holder. A domain invariant is follow-up work.
- **Impersonation session store is in memory**, so the D9 liveness check is only correct with a single replica (acceptable for v0.2, ADR 0030). A Redis-backed store is follow-up work.
- **Redis-backed rate limiter** (D11) is deferred with ADR 0030; limits are per replica until then.

## Fitness function

`TestArch_MutatingRoutesRequireAuthorization` (in `internal/architecture/authz_arch_test.go`) fails when ANY registered route, GETs and the IGNORE group included, carries no permission gate. The sole escape hatch is `selfServiceRoutes`, a pinned list whose entries each carry a reason (public credential and emailed-token flows, self-service on the caller's own identity, handler-inline authorization mandated by ADR 0044 / ADR 0053 / ADR 0055 section 8, infrastructure served by `cmd/api`); it is asserted exactly, so a route missing from it fails and an entry that no module registers, or that does carry a gate, fails. Every arch gate that reads registrations (this one, `TestArch_EveryRouteIsScopeClassified`, `TestArch_EveryAuthenticatedRouteHasMiddleware`, `TestArch_RouteHasSpecOperation`, `TestArch_HTTPMethodExplicit`) shares ONE scanner (`route_scan_test.go`, `go/parser` + `go/types`, so identifiers resolve to real objects) that reads every non-test file of the repository once. Files under each module's `ports/` (not `subscribers/`) and `cmd/api/*.go` are the API routes the gates judge; a registration anywhere else (`internal/common`, `adapters/http`, a `cmd/api` subdirectory, any other module directory) fails unless the file is in the pinned, exactly-asserted `pinnedRegistrationFiles` (the `obs` admin and health muxes, and the lookup-only mux in `authn/scope_policy.go`, each with its reason). Files whose `//go:build` constraint cannot hold in a production build (`integration`, `ignore`, custom tags) are skipped; every other constraint, `go1.1` and `linux` included, is scanned. A registration must be the plain form `mux.Handle("METHOD /path", gate(handler))`: method-less patterns, patterns in variables or loops, registrations inside function literals (local helpers, package-level `var _ = func(){...}()`), the default mux, and any `(*http.ServeMux).Handle/HandleFunc` bound as a method value or expression without being called are offences. Gates are `authn.<Factory>` selectors whose qualifier resolves to the authn import path, or variables bound once and never written again (any reassignment, `&x` or shadowing drops the alias); tags come only from the callee chain and the last (handler) argument of each call, never from an ignored argument. Route-to-spec parity remains gated by `TestArch_RouteHasSpecOperation`.

`TestArch_EveryRouteIsScopeClassified` (in `internal/architecture/scope_classification_arch_test.go`) fails when a registered route is not exactly one of IGNORE, REJECT, path-tenant, or honour + a permission gate evaluated in the scoped tenant; when a scope marker is wrapped inside the auth gate (it would run after the scope is applied and do nothing); or when the set of routes marked `TenantScopeWritable` differs from the explicit list in that file, so additions are deliberate.
