# ADR 0037 — sqlc generated-code package layout: dedicated `db` subpackage

**Status:** Accepted
**Date:** 2026-05-10

## Context

ADR 0004 locked the DB layer stack (sqlc + pgx/v5 + squirrel + goose) but left the *placement* of sqlc-generated code unspecified. Phase 1 shipped with the generated `*.sql.go` + `models.go` + `db.go` files emitted directly into `internal/identity/adapters/` alongside hand-written `*_pg.go` repositories that wrap them. The two file groups shared the same `package adapters`.

Phase 1.5 surfaced the question: is co-locating generated and hand-written code the right shape, or should the generated package be split? Two patterns are documented in the wider Go ecosystem:

- **Pattern A (co-located)** — generated `*.sql.go` + hand-written `*_pg.go` share one package. ThreeDotsLabs Wild Workouts uses this shape for its gRPC stubs (the closest TDL analogue, since Wild Workouts itself doesn't use sqlc — it uses Firestore).
- **Pattern B (split subpackage)** — generated code lives in a dedicated subpackage (e.g. `internal/dbsqlc/`); hand-written code imports it and qualifies references (`db.Queries`, `db.IdentityPerson`, `db.InsertPersonParams`). Brandur Leach's `river` queue uses this shape (`riverdriver/riverpgxv5/internal/dbsqlc/`).

Constraints inherited from preceding ADRs:

- ADR 0002 — domain layer is framework-free; no domain code may import the adapter package.
- ADR 0004 — sqlc is the canonical query generator; generated files are committed (no build-time `sqlc generate`).
- CLAUDE.md "Three unbreakable rules" — modules NEVER reference each other's `domain/`, `app/`, `ports/`, `adapters/`. The architectural intent is that adapters are the *outermost* layer; the question is whether generated query types deserve a further indirection inside the adapter boundary.

Non-goals for this ADR:

- Not changing the choice of sqlc (locked by ADR 0004).
- Not changing the per-module adapter package shape (locked by ADR 0002 + Hexagonal canon).
- Not introducing a `Querier` interface (`emit_interface: false` stays — the adapter wraps `*Queries` directly; no test-double contract needed because the adapter itself is the test seam).

## Decision

**Pattern B — generated sqlc output lives in a dedicated `db` subpackage one level below the hand-written adapter.**

Concretely for the identity module:

```
internal/identity/adapters/
├── db/                          # GENERATED — package db
│   ├── db.go                    # *Queries, DBTX, New(...)
│   ├── models.go                # Identity*, AppCommandIdempotency, ...
│   ├── persons.sql.go           # per-input-file query methods + *Params / *Row
│   ├── memberships.sql.go
│   ├── roles.sql.go
│   ├── tenants.sql.go
│   ├── refresh_tokens.sql.go
│   └── outbox.sql.go
└── *_pg.go                      # HAND-WRITTEN — package adapters
                                 # imports db, qualifies as db.Queries etc.
```

`sqlc.yaml`:

```yaml
gen:
  go:
    package: db
    out: internal/identity/adapters/db
```

Hand-written repositories embed `*db.Queries`:

```go
type PersonRepository struct {
    pool *pgxpool.Pool
    tx   *pg.Transactor
    q    *db.Queries
}

func NewPersonRepository(pool *pgxpool.Pool, tx *pg.Transactor) *PersonRepository {
    return &PersonRepository{pool: pool, tx: tx, q: db.New(pool)}
}
```

Param + row types from generated code are referenced as `db.InsertPersonParams`, `db.GetPersonAndActiveMembershipByEmailRow`, etc. Method calls on `*db.Queries` are unqualified at the call site (Go resolves them through the receiver).

This pattern applies to every module that adopts sqlc going forward — Platform, CRM, Orders, etc. all emit to `internal/{module}/adapters/db/` with `package db`.

## Consequences

**Positive:**

- **Hard import boundary.** Domain, app/, and ports/ packages cannot accidentally `import "...identity/adapters/db"` and reach generated query types — the import path itself is a code smell that surfaces in review. Pattern A relies on package discipline alone (the generated types are exported and visible from anywhere that imports the adapter).
- **Mechanical clarity.** Anyone landing in the codebase sees one folder of generated DO-NOT-EDIT files and one folder of hand-written code. No need to grep file-by-file for the `// Code generated by sqlc. DO NOT EDIT.` header to know which is which.
- **sqlc regeneration is safe.** `sqlc generate` writes only inside `internal/{module}/adapters/db/`; hand-written files in the parent are physically out of reach. Pattern A relies on file-name conventions (`*.sql.go` vs `*_pg.go`) to keep regeneration from clobbering hand-written code — a convention sqlc itself doesn't enforce.
- **Matches Brandur canon at scale.** river-queue is the most-cited public reference for sqlc + pgx production usage (CLAUDE.md cites Brandur as the Tier-1 source for this exact stack). Following the same shape lowers the cost of cross-referencing river patterns when extending the data layer.

**Negative:**

- **Extra import + qualification verbosity.** Every reference to a generated type carries a `db.` prefix. ~50 sites across 8 hand-written files in the identity module. Mitigation: trivial mechanical change (one-shot perl regex when migrating; future code is written qualified from day one).
- **Two packages instead of one inside the adapter.** The hand-written file's `package adapters` and the generated code's `package db` create a small mental tax compared to "everything in `package adapters`". Mitigation: the boundary IS the value — that's what enforces the import barrier.
- **Diverges from the closest TDL Wild Workouts analogue.** Wild Workouts co-locates gRPC-generated stubs with hand-written adapters. CLAUDE.md cites TDL as authoritative; this ADR follows Brandur instead because TDL has no published opinion on sqlc layout (Wild Workouts uses Firestore, not SQL — so the gRPC analogy is structural-only).

## Alternatives considered

1. **Pattern A — co-located generated + hand-written code in one `adapters` package** (the prior shape). Rejected. Worked at Phase 1 scale (one module, ~6 SQL files), but as more modules adopt sqlc the import-barrier-by-convention approach scales worse than import-barrier-by-package. The TDL gRPC analogue is structurally similar but operationally different — gRPC stubs are typically consumed from the same adapter that owns the wire contract; sqlc query types are consumed by repository implementations *inside* the adapter package, making the barrier-as-package distinction more valuable.

2. **Generated code in a top-level `internal/dbsqlc/` package shared across modules.** Rejected. Violates ADR 0001 (modular monolith — each module owns its schema; no cross-module DB types). Each module's `db` subpackage is private to that module's adapter.

3. **`emit_interface: true` to expose `Querier` interface for test doubles.** Rejected. The hand-written repository is itself the test seam — domain tests use fakes that satisfy `domain.Repository`, integration tests hit a real testcontainers Postgres. Adding a third indirection between repo and `*Queries` doesn't pay rent.

4. **Generated code under `internal/identity/adapters/sql/` to mirror the queries directory** (which already lives at `internal/identity/adapters/sql/`). Rejected. Confusing — `sql/` already means "the .sql input files for sqlc"; reusing it for output would conflate input and output. `db/` is unambiguous and matches Brandur's `dbsqlc` convention (shortened since the `db/` is already nested under `adapters/`).
