# ADR 0069 — Rank hierarchy and grant authority: tiers, acting downward, the grant ceiling, approvals and owner invariants

**Status:** Accepted; text is as built at merge (this ADR was written on the unmerged branch `fix/identity-authz-and-bff-security` and is not on `main`, so it was corrected in place until the merge; it is sealed from then on)
**Date:** 2026-11-20
**Supersedes (in part):** [ADR 0055](0055-permission-elevation-approval-workflow.md) §4 (approver rule) and §8 (approve/deny inline check); amends [ADR 0068](0068-authorization-hardening.md) D3 (re-stated in the domain), D4 (moved into commands, symmetric, delta-based) and D5 (the permission-request routes stay authentication-only at the route; the authorisation lives in the commands' policy)
**Builds on:** [ADR 0036](0036-permission-model.md), [ADR 0045](0045-scoped-jwt-impersonation-act-claim.md), [ADR 0058](0058-role-hierarchy-as-join-table-aggregate.md), [ADR 0062](0062-tdl-test-pyramid-fakes-canon.md), [ADR 0068](0068-authorization-hardening.md)

This ADR describes the system AS BUILT on branch `fix/identity-authz-and-bff-security` at the last commit of hierarchy fix round 6 (the commits that introduced and then corrected it). Every rule names the file that implements it. Where a rule is a default taken without an explicit owner ruling it is listed in [Pending owner confirmation](#pending-owner-confirmation) and marked `[pending]` where it is stated.

## Context

Independent security reviews and six fix rounds found one family of defects: ADR 0068 D4 ("no grant beyond your own authority") was enforced only in the HTTP port, outside the transaction; removals were unbounded; the approval path ignored it; the manager link made someone an approver with no authority check; and every check read facts (the actor's own rank and permissions, a role's holders, the owner set) outside the lock that protects the write. The attack walks that closed them are in `cmd/api/*_e2e_test.go`.

The owner's ruling, verbatim: *"Owners above admin above manager above team lead above users … Admin sits above all. If manager is not there admin can see through everything and can approve everything."* Managers hold the day-to-day work permissions; admins hold tenant-wide authority.

## Decision

### D1 — Rank and tiers

A member's **rank** is the numerically lowest `HierarchyLevel` among their LIVE roles (`internal/identity/domain/authority/rank.go`, `RankOf`). Lower is more senior; seniority is strict (equal rank is not outranking). A member with no live role has `RankNone` (99). Rank comes from roles only: overrides never change it.

| Tier | Rank / band | Seeded roles (`internal/identity/app/seed/role_catalog.go`) |
|---|---|---|
| owner | 0 | Company Owner |
| admin | 1–10 | Administrator (10), Office Administrator (10) |
| manager | 11–20 | Senior Manager (15), Sales / Purchase / Dispatch / HR Manager (20) |
| team_lead | 21–30 | Team Lead (30) |
| user | 31–99 | the Executives (50) |

`Rank.Tier()` maps a rank to its band; a value outside [0, 99] is no rank and reads as the user tier, never owner. `levelOf` counts level 0 as `RankUser` on any role that is not the Company Owner system role, so a stray level-0 custom role fails closed. Level 0 exists only on system-default roles, created by `role.New`; `Role.ChangeHierarchyLevel` refuses level 0 for every role (a system-default role is refused first, `internal/identity/domain/role/role.go`); a created or re-levelled role is in [1, 99] for every actor, super users included (`validLevel`, `policy.go`).

**Rank claim and its staleness bound.** The rank travels as the JWT claim `rank`, minted from the same role load as the permission claims at login and refresh (`internal/identity/app/permissions`, `internal/identity/app/command/rank_claim.go`). A token without the claim reads as `RankNone` (fail closed). The claim is at most one access-token lifetime stale (`jwt.AccessTokenTTL`, 10 minutes). **Staleness bound.** Authority commands decide on the stored facts at the instant of the request (D2; the actors D2 lists as not re-read excepted), so for them nothing is stale. Other modules' route gates read the token. A change that rotates the person's stamp (every item in the D2 rotation list) ends the old token at the next request, at most the stamp-cache window later when the cascade is down (30 s, `cache.SecurityStampTTL`). A time-bound grant that merely EXPIRES rotates nothing: its permission stays in the token until the token expires, up to the access-token lifetime (10 minutes). `GET /auth/me/capabilities` exposes `rank` and `tier`, computed from the same `authn.AuthorityFrom`, so the UI never has a second opinion.

### D2 — One decision point, one transaction, facts read inside it

The pure package `internal/identity/domain/authority` is the only place an authority decision is made. It imports no `app`, `ports`, `adapters`, SQL or `net/http`, never calls `time.Now()` (callers pass the decision instant) and declares one `var` per error sentinel. The zero `Actor` and the zero `Member` deny every decision; ids are compared only in canonical form.

* `authority.Actor` is built once by the port from verified claims (`authn.AuthorityFrom`, `internal/identity/ports/authn/authority.go`) and carried in every authority command (`Actor authority.Actor`). The actor's tenant comes from the claims, never from the re-bound request scope.
* `authority.Member` is the projection of a membership (`MemberOf`): rank, owner / super-admin flags, whether the person can act, manager, live overrides, and the effective level of each live role. It is built by one loader, `authorityFacts` (`internal/identity/app/command/authority_support.go`; `project`/`memberFrom` for one membership, `projectBatch` for many with a fixed number of reads).
* **Every authority command runs through one writer**, `authorityWriter.locked` (same file): one `UnitOfWork` transaction under the target tenant's RLS scope; the per-tenant advisory lock (`pg_advisory_xact_lock`, `internal/identity/adapters/sql/authority_lock.sql`) is taken FIRST; the acting member is re-read; then the command decides and writes on facts loaded in that transaction. `updateMember` (membership commands) and `updateRole` (role commands) are thin wrappers that end in `locked`. The fitness function in this ADR enforces that no command bypasses it.
* Membership saves take a row lock: `UpdateByID` loads the membership `FOR NO KEY UPDATE` (`GetMembershipByIDForUpdate`, `internal/identity/adapters/sql/memberships.sql`), so a concurrent writer waits and persists on what the previous one committed; `FOR NO KEY UPDATE` rather than `FOR UPDATE` so a foreign-key check on `role_assignments`, `reports_to` or `created_by` does not block. The person row is locked the same way for every `PersonRepository.UpdateByID`, and the permission-request row the same way for every `PermissionRequestRepository.UpdateByID` (`GetPermissionRequestByIDForUpdate`, `permission_requests.sql`), so approve, deny and cancel of one request serialise on it. The role row is NOT row-locked: role writers are serialised by the tenant lock, which every one of them holds. See [Lock order](#lock-order) for what each command takes.

**Fresh actor under the lock.** `authorityFacts.freshActor` re-reads the acting member's membership, roles and person inside the transaction and `Actor.NarrowedBy` returns the actor the policy decides with: the MORE JUNIOR of the token's rank and the stored rank, and the INTERSECTION of the token's permissions with the ones resolved now (`tenant.admin` expanded on both sides by the one `effectiveSet`). A token can only ever lose authority relative to the stored facts. A missing, inactive or cannot-act actor (inactive membership; person suspended, anonymised or deactivated; a login lock is NOT one, see pending item 19) becomes the zero actor: 403 `forbidden`. Not re-read (`Actor.NeedsFreshFacts`, `internal/identity/domain/authority/actor.go`): impersonation sessions (synthetic membership; see "Impersonation sessions are alive" below), operators acting under the cross-tenant exemption (their authority is the platform permission, not a membership of that tenant) and super users acting in a tenant other than their own (bounded by the security stamp). A super user acting in their OWN tenant, the platform tenant where they hold the super-admin role through a real membership, is re-read like anyone else, and `NarrowedBy` returns the zero actor unless that membership still holds a live super-admin role (`TestAuthorityCommands_ASuperUserInTheirOwnTenantIsReRead`). An operator acting in their own tenant follows rank and is re-read. The same re-read supplies `holdUntil` for the approval expiry cap (D8).

**Stamp rotation on authority changes.** The TARGET person's security stamp is rotated in the same transaction (`Person.RotateSecurityStamp`, event `PersonSecurityStampRotatedV1`, evicted from the stamp cache by the existing subscriber) when an authority change was recorded: role assigned (`role_assigned`), revoked (`role_revoked`), overrides replaced (`overrides_replaced`), deactivated, reactivated, an approval (`permission_approved`, the requester), and a change to the DEFINITION of a role (`role_definition_changed`, every active holder, D6). A change that leaves the target as it was rotates nothing: an idempotent role assignment, deactivation or reactivation records no event (`Membership.HasPendingEvents`), an overrides save whose live state equals the stored one writes nothing at all (`Overrides.Equal`, `errNothingToWrite` in `authority_support.go`, `user_authz.go`), and a role edit that leaves the definition equal rotates nobody (the definition is compared before and after). EVERY approval rotates the requester (an approval always records a permissions event, even when the grant was already held). Manager changes, profile edits, denials and cancellations rotate nothing. No refresh family is revoked by the rotation, so the next request with the old access token answers 401 `stale_token` (`WWW-Authenticate: Bearer realm="leadkart"`), the BFF refreshes silently and the new token carries the new rank and permissions; deactivation additionally revokes families through the existing membership-deactivated cascade. Stamp cache TTL is 30 s (`cache.SecurityStampTTL`); with the cascade down that window is the fallback.

**Impersonation sessions are alive.** An impersonation token (one with an `act` claim) is accepted only while its session is: `authn.RequireFreshStamp` (`internal/identity/ports/authn/security_stamp.go`), the one middleware every authenticated route passes (RequirePermission, RequirePlatform and RequireTenantPermission are built on it), asks the same validator value it already holds, through `authn.SessionValidator`, whether the session named by the claim is in the impersonation store, has not expired, belongs to the token's operator (`act.sub` must also equal the token subject) and targets the token's tenant (`SecurityStampValidator.IsSessionLive`, `internal/identity/adapters/security_stamp_cache.go`, over the same `impersonation.Store` the session commands use). Otherwise 401 `stale_token`. A validator that cannot answer refuses every impersonation token (fail closed); a store failure is 401 `unauthenticated`. What ends a session: `DELETE /platform/impersonation/sessions/{id}` (`EndImpersonationSessionHandler`), its expiry (the store reads an expired session as absent), and any rotation of the operator's security stamp, which the token carries and which the existing stamp check compares first: the operator's own roles or overrides changing (so losing `platform.impersonation.manage` that way ends it), a role-definition edit, a password change, a global suspension. Cost: an ordinary token has no `act` claim and pays one nil check, no I/O; an impersonation token pays one mutex-guarded in-process map read (the store is in-memory in this build, so no second cache exists; a remote store would need the stamp-cache facade pattern). **Deployment constraint (open).** The impersonation store is per process. `docker/compose.prod.yml` runs one `api` service and no replicas, which is what makes this correct today; with more than one API instance a session ended on one instance stays alive on the others, and a session created on one is unknown (401) on the others. The Redis already deployed for the stamp cache is not used for sessions: `impersonation.Store` also needs `ListByOperator`, which the stamp facade (`HybridCache`) has no shape for, so a Redis-backed store is a separate adapter behind the same interface (`cmd/api/main.go` is the only place that changes). The application cannot detect the number of replicas, so there is no start-up warning; this is recorded as a deployment constraint, not enforced. Proof: `cmd/api/impersonation_liveness_e2e_test.go` (an authority route and another module's route answer 200 while the session is live and 401 `stale_token` once it is ended).

**What a session can never reach (the refusal list).** An impersonation token is refused with 403 `impersonation_not_allowed` on the platform plane (every `/api/v1/platform/` route except two: no sub-impersonation, no listing or ending sessions, stats, person administration, the marketplace purchase that spends tenant lead credits, lead-credit top-ups) and on the pinned `authn.impersonationRefusedRoutes` (`internal/identity/ports/authn/session_policy.go`): tenant registration, the lifecycle commands (suspend, activate, mark-for-deletion, restore), omni-search, user anonymisation, and the self-service routes that act on "the caller" (change password, change email, sessions, own activity, and submit/approve/deny/cancel of permission requests). ONE check does it, in `RequireFreshStamp` next to the stamp and session checks, keyed on the matched route pattern; a dead session is 401 `stale_token` before any refusal. The check fails CLOSED: a request with no route pattern is refused, and a pattern with no method is read as a path. Not every `/api/v1/platform/` route is platform-wide: `GET /api/v1/platform/marketplace/leads` and `GET /api/v1/platform/lead-credits/balance` are tenant-plane reads gated by tenant permissions, so they are exempt (the pinned `authn.ImpersonationOpenPlatformReads`, two exact patterns, pinned again in the arch test), so an operator supporting a tenant can see its balance; the purchase and the top-up stay refused. `GET /auth/me/capabilities` and the two permission-request reads stay open. `TestArch_ImpersonationToken_RefusedExactlyWhereTheListSays` serves every registered route with a session token and pins the list exactly, requires every platform-anchored route to be refused, and makes a new self-service route (no permission gate) decide: refused, or pinned open. Every AUTHENTICATED route under `/api/v1/auth/`, whatever its gate, must be in exactly one of two pinned sets (refused, or open: `impersonationOpenAuthRoutes`), so a later `POST /auth/mfa/enroll` or `/auth/api-keys` gated by a permission `tenant.admin` implies fails the test until it is decided (`undecidedAuthRoutes`, pinned with synthetic offenders). The audience rule lives in the one verifier: `jwt.Verify` accepts exactly one audience from the closed set and requires `aud = leadkart-impersonation` if and only if the `act` claim is present, so an ordinary token never passes as an impersonation token or the reverse. Every write by a session carries the operator (`act_operator_id` and the session reason) on its outbox rows in every module (`TestE2E_Impersonation_WritesInEveryModuleCarryTheOperator`: identity, inventory, tasks).

**A session can create a member that outlives it (accepted risk, recorded).** `POST /api/v1/users` is open to a session (it is not on the refusal list): the operator chooses an email and a temporary password, may assign roles below Admin, and the person later logs in with no `act` claim. The same capability exists WITHOUT impersonation: a platform operator sends `X-Tenant-Id` (ADR 0039) and `POST /users` is a `TenantScopeWritable` route, so it is writable in the scoped tenant (`TestE2E_TenantScope_HeaderForOperatorsOnly` creates a user in a foreign tenant this way). What is recorded at creation, on both paths: the outbox and audit rows carry `act_operator_id` (the operator) and the act reason (the session's reason; `tenant-via-header` on the scope path), and the creator membership is empty (the synthetic membership is not a row, and the operator's own membership must not be stamped into another tenant). What is NOT recorded later: the new member's own logins, tokens and actions carry no `act`, and nothing on the person marks them as operator-provisioned except the creation rows. The member is created with `must_change_password`, so the operator-chosen password stops working at the member's first change, but until then the operator holds a working credential. Alternatives, not chosen: refuse `POST /users` for sessions (the scope-header path would still exist, so this alone closes nothing); require the invited person to set their own password through an emailed link, so no operator-known credential exists (a change to the create-user flow for every caller). Decided by the owner on 2026-11-21 (decision (d)): ALLOWED. Notifying the owner of a company when an operator adds a member, and an invite link instead of an operator-chosen temporary password, remain future options; neither was requested.

### D3 — Acting on a member

`Actor.MayActOn` (`policy.go`) is the basis of every membership command: a valid actor and member; super users may act on anyone; a member holding a super-admin role only by a super user; self is refused (`ErrSelfTarget`); an exempt operator acts on any member of another tenant; otherwise the member must be in the actor's tenant and the actor must STRICTLY outrank them, except that an owner may act on another owner.

* **Assign / revoke a role** (`MayAssignRole`, `MayRevokeRole`, `mayTouchRole`): `MayActOn`; the role belongs to the target's tenant; the Company Owner role is subject to the ownership gate (D9); a super-admin role only by a super user; the role's level strictly below the actor (owners: any tenant role; exempt actors: any); an assigned role must be live; the role's whole permission set must be within the grant ceiling (D4). A deleted role is revoked on rank alone so its holders can always be cleaned up. Revoking the Company Owner role runs `GuardLastOwner`.
* **Overrides** (`MayChangeOverrides`): `MayActOn`; lifting a revoke needs the Admin tier (`mayUnrevoke`, D4 below) `[pending]`; the DELTA between the member's live snapshot (taken by `MemberOf`, never caller-supplied) and the requested state is checked against the ceiling (names added, removed, re-timed; revoked names added or removed); an owner's `tenant.admin` cannot be revoked (`ErrOwnerProtected`). A permission is CONFERRED only by an actor who holds it durably (D4, `mayConfer`). A save that leaves the live overrides unchanged writes nothing and rotates nothing (D2). The command computes the new state inside the transaction: a name that stays a live grant keeps its expiry, every other granted name is permanent (the overrides route has no expiry field); a revoked list is deduplicated and a name in both lists is 422 `validation_failed` before anything is locked.
* **Deactivate / reactivate** (`MayDeactivate`, `MayReactivate`): `MayActOn`; an owner target needs the ownership gate (D9); deactivating also runs `GuardLastOwner`. Reactivating a membership of a person who is already ACTIVE in another company is 409 `person_active_elsewhere` (`ErrPersonActiveElsewhere`: the adapter maps the `uq_memberships_person_active` violation to `membership.ErrAlreadyActive`, `ReactivateUserHandler` to the command error; nothing changes).
* **Managers** (`MayReplaceManager`, `MayClearManager`, `maySetManager`, `mayUnlinkManager`): `MayActOn` the subordinate FIRST (so a caller who may not act learns nothing about the chain), then the manager must exist, be an active member of the same tenant and be STRICTLY more senior than the subordinate, and the actor must be at least as senior as the manager (self-appointment is allowed: it cannot grow authority, because approval needs `identity.roles.approve` and is capped by the approver's own permissions); replacing or clearing needs the actor to be the current manager or to strictly outrank them. Cycles: a bounded walk of the proposed manager's chain (`maxManagerChainDepth` = 64; a deeper chain is refused too), a DB `CHECK (reports_to <> id)` (`migrations/20261120000002_membership_reports_to_not_self.sql`), and approval re-checks that the approver outranks the requester, so a stale upward link is inert.
* **Profile edit of another member** (`UpdateUserProfileHandler`): `MayActOn`; editing oneself is unchanged and decides nothing. No stamp rotation.
* **Person-level guards** (`PersonChangeGuard`, `person_change_guard.go`): global suspension and anonymisation of a person run `GuardLastOwner` for every tenant the person is an ACTIVE member of, each under its own tenant lock, and apply the change inside the last guarded transaction after taking the person row and re-reading the memberships; if the active set changed, the guard restarts (3 attempts, then 409 `person_memberships_changing`).

### D4 — The grant ceiling

`Actor.mayChangePermissions` (`policy.go`) answers "may the actor confer OR remove every name in this set": unknown or empty names are refused for everyone, super users included; a super user may change anything else; `tenant.admin` only by an owner who holds it (or an exempt operator holding `platform.tenants.ownership`, D9); platform-reserved names (`permission.ImpliedByTenantAdmin` false) only by super users; every other name only if the actor holds it (`Actor.holds`: their own effective set; an exempt operator holds what `tenant.admin` implies, never platform-reserved names and never `tenant.admin` itself). Only the DELTA is checked: a role replace checks `Delta(current, new)`; role grant / revoke checks the one name when it changes anything; deleting a role checks the role's whole set (it is removed from every holder).

**Conferral needs a durable hold `[pending]`.** `Actor.mayConfer` (`policy.go`): an actor who holds a name ONLY through a time-bound grant (`Actor.holdUntil`, recorded by the fresh read) may not hand it to anyone: not through the overrides route (a name newly granted, granted for longer, or lifted off the revoked list: `conferredByOverrides`), not by granting or replacing a permission on a role, or assigning a role that carries it: 403 `grant_exceeds_authority` (creating a role confers nothing: `POST /roles` takes no permissions). Removing a name is not conferring it. Approvals are bounded instead of refused (`CapApprovalExpiry`, D8), with ONE exception: approving a name that is on the requester's REVOKED list is an un-revoke, which is decided by the overrides policy (`MayChangeOverrides`), so it IS refused (403 `grant_exceeds_authority`, the approval stays pending) when the approver holds that name only time-bound (`TestApproval_RevokedNameHeldOnlyTimeBoundIsRefusedNotCapped`).

**Un-revoke `[pending]`.** An explicit revoke is a deliberate denial. Removing a name from a member's REVOKED list, by an overrides change or by approving a request for a revoked name, additionally needs the actor to be Admin tier or above (rank ≤ 10; an impersonation session counts; exempt actors pass) (`mayUnrevoke`); a manager or team lead gets 403 `grant_exceeds_authority`, and an approval stays pending. Putting names ON the revoked list is unaffected.

### D5 — Roles

Role commands (`internal/identity/app/command/role_management.go`) decide through the same writer (`updateRole`, `locked`).

* **System-default roles are immutable for everyone** (`mayMutateRole`, `role.ErrSystemDefault` → 409 `role_system_default`): rename, re-level, delete and every permission change, super users included, so Company Owner always holds `tenant.admin` at level 0. Other seeded roles are ordinary tenant roles.
* Super-admin roles are editable only by super users. A new level is in [1, 99]; the actor must be strictly more senior than the role's current level and its new level unless exempt in that tenant. Creating a role: level in [1, 99] and strictly below the actor in the actor's own tenant (exempt actors: any tenant), initial permissions within the ceiling, an optional parent that is live, in the same tenant and strictly more senior than the child (`parentEligible`).
* **Role-parent edges (ADR 0058) are metadata**: they carry no authority (rank is level-only; the approver chain is `reports_to`). `MaySetRoleParent` requires only that the actor may edit the child and that the parent is live, same-tenant and strictly more senior.
* **Role-in-use**: deleting a role held by an ACTIVE member is 409 `role_in_use` with `errors.active_holders`; a role held only by inactive members is deleted and those assignments are revoked in the same transaction. Authority is answered before role-in-use.

### D6 — Editing a role is acting on everyone who holds it, active or not `[pending]`

A role's level need not match its holders' ranks, so the role-level checks alone let a manager confer on or strip permissions from peers and seniors, and let a member make a time-bound permission permanent by granting it to a role they hold. `Actor.mayChangeRoleFor` (`policy.go`) is the ONE place the rule lives: grant, revoke, replace, delete and a re-level are decided with the role's holders (`authority.RoleHolders`, a parameter of `MayGrantRolePermission`, `MayRevokeRolePermission`, `MayReplaceRolePermissions`, `MayDeleteRole`, `MayEditRole`, so no command can leave them out), and the actor must be allowed to `MayActOn` every holder, ACTIVE OR NOT (a locked or suspended person is still a holder); an inactive holder counts too, fail closed, because reactivation does not re-check what their roles now confer (whoever outranks them can still remove the role from them). A holder who is the actor is refused (`self_modification_forbidden`), except an owner (rank 0): an owner holds `tenant.admin` and gains nothing by editing a custom role they also hold, and a sole owner could otherwise neither edit it nor drop it. A rename acts on nobody; a re-level to the level the role already has changes nobody.

* **Re-level reporting rule** (`reportingHolds`): a re-level is refused, 422 `role_level_breaks_reporting`, only for a reporting line it NEWLY breaks: a line that was strictly ordered before the move (holder junior to their manager, or a direct report junior to the holder) and is not after it. A line that is already broken does not block (ordinary commands can leave such lines behind: assigning or revoking a role changes rank without looking at `reports_to`), and an inactive manager or direct report is ignored; inactive holders are skipped. A holder's new rank is the most senior of the new level and the levels of the other live roles they hold (a deleted role never counts). The rule binds every actor (it is data integrity); a manager that was not loaded fails closed.
* **Loads and cost** (`authorityFacts.roleHolders`): holders are loaded once per command with a FIXED number of repository reads whatever their count: `ListHoldingRole` (any status), one role read, one person read; a re-level adds ONE targeted read, `ListReportingLinks` (the holders' managers and direct reports, `memberships.sql` `ListMembershipsLinkedTo`, indexed by `idx_memberships_reports_to` and the primary key). That read is bounded by the holders' reporting lines (their direct reports plus their distinct managers), never by the size of the tenant (the whole-tenant read it replaced is gone). The stamp rotation is one person write per ACTIVE holder (the per-person security-stamp event requires it) and is the only cost that grows with holders. Tests: `role_holders_test.go` (reads equal over 3 and 30 holders; rotations equal the active holders; 40 unrelated members are never read), `membership_repository_pg_test.go` (the SQL contract).
* **Stale tokens end**: `updateRole` rotates every active holder's stamp in the same transaction when the role's permissions, level or deleted state changed (D2). A rename rotates nothing.

### D7 — Last-owner and owner invariants

`GuardLastOwner` refuses deactivating or demoting an owner when no OTHER active owner of the tenant remains (the target's own activity does not matter; an inactive owner, a non-owner, an invalid member or another tenant's owner never counts as "another owner"); it binds every actor, super users included, and the person-level guard applies it across tenants. `guardOwnerOverrides` refuses revoking `tenant.admin` from an owner (`owner_protected`). Tenant registration assigns the first Company Owner outside the writer (a brand-new tenant has no other member; pinned in the fitness function's exception list).

### D8 — Permission requests and approvals

**Requestable set** (`permission.IsRequestable` = `ImpliedByTenantAdmin`; `permissionrequest.New` refuses anything else, approve re-checks the STORED name): the 44 catalogue names below. `identity.users.create` is requestable only by a requester at the Administrator tier or above, and approvable only for one (D11). Everything else (`tenant.admin` and every platform-reserved name) is conferred only by role.

`identity.meta.request_permission_elevation`, `identity.tenants.{view,update,update_settings}`, `identity.users.{view,create,update,deactivate,reactivate,unlock,update_permissions}`, `identity.roles.{view,create,update,delete,assign,revoke,approve}`, `crm.leads.{read,assign,manage,read_all}`, `platform.marketplace.{browse,purchase}`, `platform.lead_credits.read`, `inventory.catalog.{read,manage}`, `inventory.stock.{read,manage}`, `tasks.work_items.{read,read_all,manage,reassign}`, `dispatch.consignment_notes.{read,manage}`, `orders.quotations.{read,manage}`, `orders.orders.{read,manage}`, `orders.payments.{read,record}`, `orders.invoices.read`, `notifications.inbox.{read,manage}`.

**Not requestable** (17): `tenant.admin`, `platform.tenants.{view,create,manage,ownership}`, `platform.users.{view,create,manage}`, `platform.roles.{view,manage}`, `platform.impersonation.manage`, `platform.unverified_contacts.manage`, `platform.lead_credits.topup`, `identity.tenants.{suspend,activate,delete}`, `identity.users.anonymise`.

**Who may decide** (`mayDecide`, `MayApprove`, `MayDeny`): never an impersonation session, never the requester (`ErrSelfTarget`); a super user or an exempt operator in ANOTHER tenant; otherwise the approver must be in the requester's tenant and strictly outrank the requester, and then either (a) be Admin tier or above, or (b) be the requester's manager and hold `identity.roles.approve`. Approving additionally needs the permission to be requestable and:
* manager path: the approver HOLDS the permission;
* Admin path: the approver may approve any requestable permission WITHOUT holding it ("Admin sits above all ... can approve everything"), except the **must-hold set** `[pending]` (20 names, `adminMustHold`, `policy.go`), which an Admin-tier approver must hold themself: `identity.roles.{create,update,delete,assign,revoke,approve}`, `identity.users.update_permissions`, `identity.tenants.{update,update_settings}`, `platform.marketplace.purchase`, `orders.payments.record`, and the tenant-wide visibility names and the right to ask: `identity.meta.request_permission_elevation`, `identity.users.view`, `identity.roles.view`, `identity.tenants.view`, `crm.leads.read_all`, `tasks.work_items.read_all`, `orders.payments.read`, `orders.invoices.read`, `platform.lead_credits.read`. The other 24 requestable names are approved by the Admin tier without holding them: `identity.users.{create,update,deactivate,reactivate,unlock}` (so HR onboarding and offboarding approvals are not owner-only; `identity.users.create` is the exception to the exception: it is approved only for a requester at the Administrator tier or above, nobody approves it for a member below, decision (d)), `crm.leads.{read,assign,manage}`, `platform.marketplace.browse`, `inventory.catalog.{read,manage}`, `inventory.stock.{read,manage}`, `tasks.work_items.{read,manage,reassign}`, `dispatch.consignment_notes.{read,manage}`, `orders.quotations.{read,manage}`, `orders.orders.{read,manage}`, `notifications.inbox.{read,manage}` (`TestApprove_AdminMustHoldList`, `TestApproval_AdminMustHoldAuthorityAndMoney`: both sides of every name). What an existing tenant's Administrator can approve: it holds what its role carries; the tier migration (D10) gave a pristine Administrator the read bundle and the elevation permission but NOT `tenant.admin`, so it holds the nine visibility names of the list and none of the role, user-permission, tenant-settings, purchase or payment-recording names: it approves the 24 free names and the visibility names, and not the other eleven until an owner grants it `tenant.admin` or those names. A new tenant's Administrator holds `tenant.admin`, which implies all 20. Owners hold `tenant.admin` too.
* un-revoke: see D4.

**Expiry cap `[pending]`.** An approval never outlives the approver's own grant: when approving REQUIRED the approver to hold the permission (manager path, or an Admin's must-hold name) and the approver holds it only through a time-bound override (not through a role or a permanent grant; a timed `tenant.admin` caps every name it implies), the approved grant ends no later than the approver's (`Actor.CapApprovalExpiry`; `holdUntil` is set from the fresh read by `NarrowedBy`). The request row records the capped expiry. The cap applies to a name that is NOT on the requester's revoked list; for a revoked name the approver's time-bound hold refuses the approval instead of capping it (D4). Consequence of the two rules together: someone who holds `tenant.admin` only until a date can approve requests (capped at that date, because a timed `tenant.admin` holds every name it implies until it ends) but cannot assign roles or grant overrides (conferral needs a durable hold; pending item 20).

**Check order** (`ApprovePermissionRequestHandler`): the caller's own fresh read under the lock (a caller who can no longer act, an inactive membership or an unusable person, is 403 `forbidden`, before any 404 below) → impersonation session (403, answered before anything else is read) → the request exists, else 404 → the requester's membership exists, else 404 (`loadForDecision`) → the caller is the requester, 403 `self_modification_forbidden` (`eligibleToDecide`, first) → eligibility to decide at all, else **404** `[pending]` (`eligibleToDecide`: a caller who is not the requester and fails `MayDeny` is told the request does not exist, so the answer is no existence or rank oracle; a requester whose roles do not load is 409 `member_roles_inconsistent` for a caller who could decide anything, 404 for everyone else) → authority over this permission (403 `grant_exceeds_authority`, including the un-revoke rule) → state (409 `permission_request_not_pending`) → requestable (422 `permission_not_requestable`; a legacy stored row stays pending, can be denied or cancelled) → requester still able to receive the grant (409 `permission_request_requester_inactive`). The grant is written on the requester's row as it is under the lock: only the approved name changes, expired override rows are left untouched, and a name leaves the revoked list. Deny uses the same gate and eligibility, without "holds the permission". **Writers of one request** (approve, deny and the requester's cancel) all run under the tenant authority lock and persist through `authorityWriter.decideRequest`, whose `UpdateByID` loads the row `FOR NO KEY UPDATE` and runs the state machine on that locked snapshot: a request ends approved WITH its grant or cancelled WITHOUT it, never a mix (`TestPermissionRequestRepository_UpdateByID_WritersSerialiseOnTheRow`, `TestE2E_PermissionRequests_ApproveAndCancelNeverMix`). Cancel needs no fresh actor (the requester withdraws their own request; nothing is conferred). A timing difference between the 404 for "no such request" and the 404 for "may not decide it" (the second reads the requester's facts) is not closed: the ids are random UUIDs and the risk is low.

**Visibility and the queue.** `GET /permission-requests/{id}`: the requester and anyone who may deny it, else 404 (`AuthorizePermissionRequestViewHandler`), decided on the FRESH actor in one read transaction like approve and the queue: a viewer who was demoted, or a requester who was deactivated, since the token was minted sees nothing. `GET /permission-requests?role=approver` (`ListDecidablePermissionRequestsHandler`): the pending requests the caller may DENY, each with `can_approve` (= requestable and `MayApprove`), decided on the fresh actor so `can_approve` is what approve answers. A caller who can decide nothing (`MayDecideAny`: below the Admin tier without `identity.roles.approve`, an impersonation session) gets an empty page with no read; a decider below the Admin tier (`DecidesWholeTenant` false) is scanned only over their own reports (the filter is in the SQL, `ListPendingPermissionRequestsInTenantPage`); the rest runs in one read transaction: one list, one batched membership read (`membership.Repository.GetByIDs`), one role read, one person read, bounded to a window of 100 requests.

### D9 — Platform operators

* **Cross-tenant exemption** (`operatorExempt`, `exemptOperatorIn`): a slug-anchored, non-impersonation platform operator holding `platform.users.manage` or `platform.roles.manage` acts on members and roles of ANOTHER (canonical, valid) tenant without rank, holding what `tenant.admin` implies there but no platform-reserved name. Inside the operator's own tenant, rank decides like anyone else. Targets that hold a super-admin role stay super-user-only, and the last-owner guard still applies.
* **Ownership gate `[pending]`** (`mayChangeOwnershipIn`, `platform.tenants.ownership`): an exempt operator needs `platform.tenants.ownership` for the decisions that change who OWNS a tenant: assigning or revoking the Company Owner role, conferring or removing `tenant.admin` by role or override, and deactivating OR reactivating an owner. Super users and every actor deciding in their own tenant are unaffected. The permission is platform-reserved, seeded to no role, not requestable. Everything else the exemption allows is unchanged.
* **`platform.impersonation.manage`** (platform-reserved) creates, lists and ends impersonation sessions; a session is **Admin-equivalent** whatever rank it claims (`NewActor` forces rank 10, never platform or super), so it cannot act on owners, assign Administrator or Company Owner, confer `tenant.admin` or remove the last owner, and it never approves (`ErrImpersonationNotAllowed`) or submits requests. The token is dead the moment its session is ended or expires (D2, "Impersonation sessions are alive").

### D11 — Who may add users: the admin-tier-only set (owner ruling 2026-11-21)

The owner's ruling, verbatim: *"SuperAdmin and Platform Team, Company Admin and Company Owner are allowed to add users only."* Read as (decision (d)): a super user and platform-team operators may add users to a company, and inside a company only the Company Owner and the Administrator tier (rank 0 to 10) may; nobody below that tier may, and the ability cannot be obtained below it by any route.

* **The set** (`authority.AdminTierOnlyPermissions`, `internal/identity/domain/authority/admin_tier.go`): exactly `identity.users.create`. Every route and command that adds a member funnels through it: `POST /api/v1/users` (`CreateUserHandler`) is the only one. Tenant registration (`POST /api/v1/tenants`, the first Company Owner of a NEW tenant) is operator-only behind `platform.tenants.create`, and the bootstrap CLI is not a route. The rule: a permission in the set is HELD and CONFERRED only at rank <= 10 (`authority.MayHoldAt`).
* **"Company Admin"** is the Administrator tier by rank (rank <= 10), not a name (the owner confirmed on 2026-11-21, decision (f), that the Office Administrator adds users): the Administrator and the Office Administrator are both level 10 and both hold `tenant.admin` in the seeded catalogue, so both add users; Senior Manager (15), Sales / Purchase / Dispatch / HR Manager (20), Team Lead (30) and the five Executives (50) do not, and the seeded catalogue never gave them the permission (`TestDefaultRoleCatalog_OnlyTheAdministratorTierHoldsTheAddUsersPermission` pins that). An existing tenant's Administrator that lost or never received `tenant.admin` (D10, Q2) does not hold `identity.users.create` until the owner grants it `tenant.admin`; that is today's behaviour, unchanged.
* **Evaluation, one place per concern.** (1) The request gate and `GET /auth/me/capabilities` (`authn.satisfiesIn`, the one authorisation decision): a tenant-plane grant, explicit or implied by `tenant.admin`, satisfies a name in the set only when the token's rank claim is <= 10 (a missing claim is no rank; an impersonation session is Admin-equivalent); a stale override, role or `tenant.admin` below the tier is inert and absent from `effective_permissions`. The platform equivalents (`platform.users.create`, `platform.users.manage` for a slug-anchored operator) and the super user are unaffected. (2) The command (`CreateUserHandler`): `Actor.MayCreateMembers` on the token before anything is read, hashed or looked up (so a refused caller learns nothing, not even that the email is active in another company), then again on the FRESH actor inside the transaction, after the tenant authority lock (the one lock order; the lock is taken before the person and membership writes), through `Actor.NeedsFreshFactsToCreate` (an actor admitted by the platform rule in another tenant has no membership there to re-read). 403 `admin_tier_required` for a member below the tier. (3) Conferral, decided by the same policy for every actor including super users and operators, because it is data integrity: `MayCreateRole` and `MayEditRole` (a role containing the name must be at level <= 10; re-levelling such a role below level 10 is REFUSED, not stripped), `MayGrantRolePermission` and `MayReplaceRolePermissions` (the role's resulting set), `MayAssignRole` (a stale below-tier role that contains it), `MayChangeOverrides` (the granted set after the change, against the target's stored rank), `Actor.MayRequest` (submit) and `mayDecide` (approve; a time-bound grant only arises from an approval). All refuse with `ErrAdminTierOnly`. A write that REMOVES the name from a below-tier role is allowed; a write that leaves it in the resulting state is not, so a stale grant surfaces and is cleaned instead of being carried forward.
* **Operators.** A super user, an operator holding `platform.users.create` or `platform.users.manage` (through `X-Tenant-Id`, or in the platform tenant), and an impersonation session pass by the platform rule and are attributed exactly as before (decision (d) closes pending item 25: ALLOWED). They cannot hand the permission to a member below the tier either.
* **tenant.admin below the tier.** `tenant.admin` is still conferrable only by owners and still implies every other requestable name. Given to a member below the tier it no longer implies `identity.users.create` (evaluation (1)); it is not itself refused there, because no other pending-owner item is decided here.
* **Existing data.** Migration `20261121000001_identity_add_users_admin_tier_only.sql` removes the permission from live roles below the tier, deletes granted overrides of it on members below the tier and cancels their pending requests for it, each change an audit row that is also Down's ledger; the application already treats the stale grant as inert, so the migration rotates no stamp. An override on a member who is demoted below the tier later is likewise inert; the member's next overrides save must drop it (evaluation (3)).
* **Proof.** `admin_tier_test.go` (authority), `create_user_authority_test.go` and `permission_request_admin_tier_test.go` (commands), `authn/admin_tier_test.go` (gate and capabilities), `route_authz_test.go`, the migration integration test, and the attack suite `cmd/api/authority_attacks_adduser_e2e_test.go` (every persona below the tier refused on `POST /users`, on role edit, override, request and approval, in a world that holds the permission as stale data; Owner, Administrator, Office Administrator, super user, operators and an impersonation session succeed).

### Lock order

One order everywhere, so no cycle: **(1)** the tenant authority advisory lock (`pg_advisory_xact_lock('identity.authority:' || tenant)`), **(2)** the permission-request row (`FOR NO KEY UPDATE`, taken by `UpdateByID`), **(3)** membership row(s) `FOR NO KEY UPDATE`, **(4)** person row(s) `FOR NO KEY UPDATE`. The role row is not row-locked (`UpdateByID` reads it plainly); role writers are serialised by (1). Every multi-row writer holds (1), so two of them cannot interleave; every command takes (1) before any row, so a writer that holds a row never waits for (1). Role delete locks several INACTIVE holders' membership rows one after another, so "a writer never waits for another membership row" is not true as stated; what makes it safe is (1): any other writer of several rows holds (1) first and so cannot be inside that sequence, and a command that locks a single membership row (deactivate, profile edit) holds (1) too and waits for nothing else while holding it. `FOR SHARE` is not used on fact loads (it would invite share-to-update deadlocks between two reactivations of one person in different tenants). What each command takes, in order:

| Command | Takes |
|---|---|
| assign / revoke role, set / clear manager (`user_authz.go`) | (1); the role is read plainly; (3) the target membership; (4) the target person on rotation (assign / revoke only) |
| overrides replace, deactivate, reactivate, profile edit of another member (`updateMember`) | (1); (3) the target membership; (4) the person on rotation (not for a profile edit; not for an unchanged overrides save, which writes nothing) |
| grant / revoke / replace permissions, re-level, delete, rename a role (`updateRole`) | (1); the role (read plainly, written last); the holders read plainly; (4) each ACTIVE holder's person on rotation; delete also (3) its INACTIVE holders' memberships |
| create role | (1); the new role row |
| approve a request | (1); (2) the request; (3) the requester's membership; (4) the requester's person |
| deny / cancel a request | (1); (2) the request |
| global suspension / anonymisation (`PersonChangeGuard`) | per tenant the person is active in, in turn: (1) that tenant; then the person row and a fresh read of the memberships inside the last guarded transaction |
| the first owner of a new tenant (`RegisterTenant`) | none of (1)-(4): the tenant has no other member |

28. **Production refuses to start without an explicit trusted-proxy decision** (controller default, pending the owner's confirmation; ADR 0068 D11): `LEADKART_HTTP__TRUSTED_PROXIES` must be a list or the word `none`; production also refuses prefixes wider than `/8` (IPv4) or `/32` (IPv6) and anything outside private, loopback, link-local, CGNAT and ULA ranges, with no override syntax. `LEADKART_ENV=production` is now set in `docker/compose.prod.yml`, which also turns on the start-up privilege refusal for an owner or over-privileged database role (ADR 0063).
29. **IPv6 clients are keyed per `/64`** for the global and per-route limiters, the failed-login lockout keys and the Argon2 per-client bound; the credential routes also count by `/48` (item 44). The idempotency scope is not keyed by client: anonymous requests are ineligible (controller default, pending the owner's confirmation; ADR 0068 D11). A carrier-grade-NAT IPv4 address shared by thousands of users is NOT widened, so those users still share a bucket.
30. **The phantom failed-login counter lives in Postgres** (controller default, pending the owner's confirmation; ADR 0068 D12): table `identity.login_phantom_failures`, HMAC key derived from the dedicated `LEADKART_IDENTITY__LOCKOUT_KEY` (required in production; the JWT-derived fallback applies only outside production, see item 43, which corrects this item's first wording), purged every 5 minutes. The alternative was a per-replica in-memory counter, which is neither restart-safe nor atomic with the real counter.
31. **`X-Command-Id` is ignored, not refused, on anonymous and `/api/v1/auth/*` requests and on safe methods** (controller default, pending the owner's confirmation; ADR 0068 D11): nothing is stored or replayed. Refusing with a 400 instead would break a client that attaches the header to every POST.
32. **Change-password has a per-person limit of 5 per minute, burst 5**, answering 429 + `Retry-After` before any password work (controller default, pending the owner's confirmation; ADR 0068 D11, `RateLimit.ChangePassword`).
33. **Argon2 runs under a concurrency cap of 16 slots with a 2 s queue timeout**, then 503 + `Retry-After` (controller default, pending the owner's confirmation; ADR 0068 D12, `Argon2.MaxConcurrent` / `Argon2.QueueTimeout`). 16 x about 19.5 MiB is about 312 MiB of LIVE Argon2 memory; that is not the container figure, because the collector needs headroom, so production sets `GOMEMLIMIT=900MiB` for the 1 GiB container (`docker/compose.prod.yml`). The owner may trade latency under a login burst against memory.
34. **The default limits** (controller defaults, pending the owner's confirmation; ADR 0068 D11). Global per client: 10 requests/s, burst 60 (fixed in `cmd/api`). Per route, per client (per minute / burst): login 30 / 10, refresh 120 / 30, request-password-reset 5 / 5, reset-password 10 / 5, confirm-email-change 10 / 5, tenant registration 10 / 5; change-password 5 / 5 per person. Each limiter holds at most 50,000 keys and refuses new keys with 429 at the cap. They are per API replica, so N replicas admit N times these rates.
35. **Two residual enumeration oracles are accepted** (ADR 0068 D12): a real account's counter also moves because of its owner (item 8 of the review), and the 300 ms reset floor hides the known-account work only while that work stays under 300 ms (measured 3.4 ms median, 5.5 ms max; raise the floor if the p99 of `request-password-reset` approaches 150 ms).
36. **Moved: decided by the owner on 2026-11-21** (see "Decided by the owner", decision (j)). The number is kept so the list is not renumbered. In force: a just-rotated refresh token is honoured for `Refresh.GraceWindow` (30 seconds), by the client that consumed it, at most 3 times (ADR 0068 D10); `Refresh.GraceWindow = 0` restores strict rotation.
37. **Moved: decided by the owner on 2026-11-21** (see "Decided by the owner", decision (i)). The number is kept so the list is not renumbered. In force: the default password policy is 8 characters minimum with an upper-case letter, a lower-case letter, a digit and a symbol (it was 12 with the same four classes); it binds the first admin of a new tenant, every member an admin creates, every reset and change in a tenant that never stored a policy, and the first operator the bootstrap CLI seeds. The default now equals the policy's validated floor (8). A tenant with NO stored policy (a zero policy: every tenant that never edited it) is checked as the default and so follows it; a tenant whose stored policy says 12 stays at 12; there is no data migration. This goes against NIST SP 800-63B's advice not to impose composition rules; the owner chose it. A tenant can still relax its own through `PATCH /tenants/{id}/settings` (floor: 8 characters).
38. **A password over 1024 bytes is refused** with `max_length` (implementer default, pending the owner's confirmation; ADR 0068 D13). The API already accepts bodies up to 1 MiB, and neither the class counting nor an Argon2id hash should run over that. 1024 bytes is far above NIST's 64-character minimum for verifiers; the stored policy's own cap on `min_length` is 128.
39. **Change-password checks the policy before it verifies the current password** (implementer default, pending the owner's confirmation; ADR 0068 D13). The plan placed it after the verification. Checking first means a refused password costs no Argon2id run and the 422 is answered even to someone who got the current password wrong; it tells that caller nothing, since any member may read their tenant's policy. A current password over the size bound is answered as incorrect without being hashed.
40. **A reset or a change applies the policy of ONE tenant, never a merge** (ADR 0068 D13): a person holds at most one active membership, so the reset reads that membership's tenant (the default when there is none), and change-password reads the tenant in the caller's own token (an operator acting in another tenant through `X-Tenant-Id` is still held to the policy of their own tenant). Were a person ever allowed several active memberships, the strictest policy among them should apply; today there is nothing to choose between.
41. **The first operator's password (bootstrap CLI) is held to the default policy** (implementer default, pending the owner's confirmation; ADR 0068 D13). A weaker `LEADKART_SUPERADMIN__PASSWORD` now stops the CLI before anything is written. The documented dev password (`LeadKart!Dev2026`) passes.

42. **The worker is part of the production compose file** (controller default, pending the owner's confirmation; ADR 0068 D12): `worker` runs beside `api` with a health check (`/worker -healthcheck`), `restart: unless-stopped`, 512 MiB, and depends on `migrate`. Without it no outbox subscriber runs (stamp-cache eviction backstop, refresh-family revocation backstop, suspension / anonymisation / deactivation cascades, audit, email) and the phantom failed-login table is never purged. The api exposes `leadkart.outbox.oldest_unacked_age_seconds` and `leadkart.identity.login_phantom_failures.rows` and warns at boot when the outbox is more than 5 minutes stale. The worker validates only what it uses (`config.LoadWorker`).
43. **A dedicated lockout secret is required in production** (controller default, pending the owner's confirmation; ADR 0068 D12): `LEADKART_IDENTITY__LOCKOUT_KEY`, base64 of at least 32 random bytes, different from the JWT key; the api refuses to start in production without it, and elsewhere falls back to a key derived from the JWT key with a boot WARN. Item 30 said the key derives from the JWT secret: that holds only outside production. Rotating the dedicated key restarts the phantom counters and opens the same short 423-versus-401 window, so it is rotated deliberately, not routinely.
44. **Password work is capped per client and a share of the gate is reserved for signed-in users** (controller defaults, pending the owner's confirmation; ADR 0068 D12): one client key holds at most 2 slots (`Argon2.MaxPerClient`); its further operations wait their turn, at most 8 waiting per key, within the queue timeout, and only a wait that runs out or a ninth waiting operation is refused with the same 503, 4 of the 16 slots reserved for change-password, create user and a reset with a valid token (`Argon2.ReservedAuthenticated`; anonymous login and registration use at most 12), and the credential routes also limit IPv6 by `/48` at 4 times the per-`/64` rate and burst. The numbers are guesses about one household or office behind one address (2 running, 8 waiting) and about the mix of traffic (4 of 16): the owner may change the first and the last by configuration; the line length of 8 is a constant in code (`argon2.DefaultMaxWaiting`) until the owner decides otherwise.
45. **Residual timing and side-effect differences between login branches are accepted** (ADR 0068 D12, residual oracle 11): the counter statement runs on `persons` versus the phantom table; the real account's crossing attempt also writes one outbox row; a right password is distinguishable by design; a no-membership person with the right password does one extra row write. None exceeds database jitter next to a 30 to 50 ms verify.
46. **A refused or cancelled attempt is not counted; one cancelled mid-verify is** (implementer default, pending the owner's confirmation; ADR 0068 D12): the gate slot is taken before the attempt is registered, so saturating the gate cannot lock an account; a request that goes away after its verify started has done the work and is counted once. The effective budget of a window is at most `MaxFailedLogins` real verifies; ten wrong passwords lock, nine wrong plus the right one signs in.
47. **A login that verified a password changed in the meantime is refused as a wrong password** (implementer default, pending the owner's confirmation; ADR 0068 D12): the session insert re-reads the person `FOR SHARE`; a hash that moved, or a person no longer active, answers 401 and creates no family. The cost is a login that straddles a change fails once instead of opening a session that would be revoked anyway.
48. **`GET /auth/me/capabilities` exposes the caller's own tenant's password policy** (`password_policy`: `min_length`, `max_length`, `requires_uppercase`, `requires_lowercase`, `requires_digit`, `requires_symbol`; implementer default, pending the owner's confirmation; ADR 0068 D13). Any member can already read the rules by failing one change; this makes them readable before the first attempt, including on the forced-change screen. An impersonation session sees the impersonated tenant's rules (change-password itself is refused to it). There is NO anonymous policy endpoint: the password-reset page learns the rule codes only from the 422 answer to a reset made with a valid token, the disclosure accepted since ADR 0068 D13.
49. **Stamp-cache eviction happens in the API process, after the commit** (implementer default, pending the owner's confirmation; ADR 0068 D12): `PersonRepository.UpdateByID` evicts the cached stamp via `pg.OnCommit` whenever a write rotated it, so an old access token stops working at once on every instance (the cache is the shared Redis, no L1) instead of up to 30 s later and only when the worker runs. A request that read the old stamp before the commit can refill the cache for at most the 30 s TTL. Item 8's "30 s with the cascade down" is now the bound only when Redis itself is down at eviction time.
50. **A client's excess password work waits instead of failing; the numbers are 2 running and 8 waiting** (controller default, pending the owner's confirmation; ADR 0068 D12, `Argon2.MaxPerClient`, `argon2.DefaultMaxWaiting`): the earlier rule refused a client's third concurrent operation at once, which would fail an office of field reps behind one NAT address who sign in together. Now the excess waits in a per-client first-in-first-out line within the 2 s queue timeout (a wait that runs out answers the same 503 on every login branch), and a ninth waiting operation is refused at once. The 8 is a constant in code, not configuration. The owner may change both numbers; a longer line or timeout lets one address hold more requests open, a shorter one fails bigger offices sooner.
51. **A reset link is dead after its expiry, a refused password is bounded, and a reset may use the current password** (controller default, pending the owner's confirmation; ADR 0068 D13, fix round 13): the token is validated (state, expiry) before any password work, so an expired link costs nothing and probes nothing (before: it earned the policy answer and a same-as-current verify, a guessing oracle for the current password). The "same as current password" check is no longer made on RESET (with a valid token it is exactly that oracle; change-password keeps it). A live token refused for its password (policy, breach list) stays usable for 5 refusals, then is invalidated (`command.PasswordResetMaxAttempts`, a constant in code). The cost: a person who "resets" to the password they already have is allowed to; the 5 is a guess, not a measured number.

In force: a session has an absolute lifetime of `Refresh.AbsoluteTTL` (14 days) from its login; the first refresh after the family is 14 days old answers `401 refresh_rejected` with `reason: session_expired` and revokes the family (`absolute_ttl`). The idle timeout (item 56) is enforced by `Refresh.SlidingTTL`.
53. **Moved: decided by the owner on 2026-11-21** (see "Decided by the owner", decision (j)). The number is kept so the list is not renumbered. In force: a refresh grace replay is accepted only from the client that consumed the token (the verified client address, stored as an HMAC binding on the token; migration `20261120000006`), at most 3 times; any other client or a fourth replay is reuse and revokes the family (ADR 0068 D10).

No tenant slug and no further identifier is added; a name is shown to those who could already read the tenant (operator and the tenant's own members).

62. **Names, titles and reasons people type cannot carry control or direction-override characters** (implementer default, pending the owner's confirmation; follow-up to D9 and D11): ONE rule, `internal/common/humantext`, applied by the aggregates on write. Refused: U+0000-U+001F and U+007F-U+009F (CR, LF and TAB included; no field is multi-line), U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069, U+2028, U+2029, U+00AD, U+034F, U+115F, U+1160, U+3164, U+FFA0, U+180E, U+200B, U+2060-U+2064, U+FEFF, U+FFF9-U+FFFC and the TAG block U+E0000-U+E007F; U+00A0 and U+3000 are allowed. As built after the first round: the zero-width non-joiner and joiner (U+200C, U+200D) are legitimate inside words of Indic and Arabic-script languages, so they are ACCEPTED when the rune before and the rune after are each a letter or a combining mark (Unicode L* or M*), and refused at the start or end, next to whitespace, digits, punctuation, symbols or another format character, and when two are adjacent; emoji ZWJ sequences stay refused (emoji are symbols). Not covered: emails, slugs, codes, passwords (own rules), statutory and address fields, the revoke-all-sessions reason (the caller's own audit text, no 422 answer). Answer: the route's existing 422 code with `errors{<field>: ["invalid_characters"]}`. Legacy data: nothing is rewritten, reads never fail; a full-replace write that re-sends a stored value unchanged is accepted, only a changed value is checked (a replayed suspend or mark-for-deletion reason equal to the stored one stays idempotent).

## Consequences

Every API change the web BFF must handle, in one table: [bff-consequences-0068-0069.md](../BFF_API_CHANGES.md).


* **Front-end (who may add users).** Show "Add member" only when `effective_permissions` contains `identity.users.create`, which now means the Company Owner or Administrator tier (or a platform operator); do not offer `identity.users.create` in the override editor for a member below the Administrator tier, in a role below level 10, or in a permission-request picker for a member below it; 403 `admin_tier_required` reads "only the Company Owner and Administrators can add users".
* **Front-end.** Hide an action on a member whose `rank` is not strictly greater than the caller's (owners: also on owners) (`/auth/me/capabilities` `rank`, `tier`). Treat 401 `stale_token` with `WWW-Authenticate` as "refresh silently": the session survives an authority change and the refreshed token carries the new rank and permissions; a deactivated member's refresh is refused. The approver queue items carry `can_approve`: enable Approve only when it is true, Deny always. Approve and deny answer 404 to a caller who may not decide the request. Role edits can answer 403 `insufficient_rank` / `self_modification_forbidden` (holders), 422 `role_level_breaks_reporting`, 409 `role_in_use`; `PATCH /roles/{id}` with no `name` and no `hierarchy_level` is 400 `invalid_body`. Reactivating a person who is active in another company is 409 `person_active_elsewhere`. An impersonation token answers 401 `stale_token` once its session is ended. 409 `person_memberships_changing` is retryable.
* Existing tenants are re-tiered only where pristine; Administrators of existing tenants do not gain `tenant.admin`; custom roles keep their levels and permissions.
* A role edit ends every active holder's session token (they refresh); an approval ends the requester's; an unchanged overrides save ends nobody's.
* Team Leads and managers do not see their team's leads or tasks until team-scoped visibility exists (Team Lead has no `read_all`); the approver queue was empty before this work.

## Open follow-ups

* **Team-scoped visibility** for managers and team leads (hierarchy-scoped lists); today `read_all` is tenant-wide.
* **Optional expiry on the overrides route** (`PATCH /users/{id}/permission-overrides` makes every new grant permanent; time-bound grants arise only from approvals).
* **Hard-delete purge saga** for tenants (`hard_delete_tenant`), so memberships, roles and their audit rows leave together.
* Reactivating a membership of a person who cannot act (suspended, anonymised) is still allowed; the person guard closes the check-then-change race, not that.
* Operators under the cross-tenant exemption and super users acting in another tenant are not re-read (their authority is the platform permission or the flag, bounded by the stamp); impersonation actors are bounded by their session. Operators and super users acting in their own tenant ARE re-read.
* Recording WHO placed a revoke, so that only someone at least that senior can lift it (needs a schema change; today any Admin-tier actor may).
* Route-level permission checks in other modules read the token (the 30 s stamp-cache window with the cascade down; up to the access-token lifetime for a time-bound grant that expires).
* A reports-to cycle trigger in the database (today: command-level bounded walk plus the self-reference `CHECK`).

## Alternatives considered

* **Port-level checks (the original D4).** Rejected: outside the transaction, so every check-then-act race (last owner, demoted actor) stayed open, and every route repeated the rule.
* **A rank per permission or per resource.** Rejected: the owner's ruling is a single ladder; permissions stay a separate axis (ADR 0036).
* **Optimistic concurrency instead of an advisory lock.** Rejected: the decision reads many rows (owners, holders, manager chain) that no single version column covers.
* **Re-resolving the actor per request instead of under the lock.** Rejected: the cost lands on every request and still races the write.
* **Rotating a per-membership "authz version" instead of the person's security stamp.** Rejected: a second invalidation mechanism; the stamp, its event and its cache subscriber already end tokens, and not revoking refresh families keeps the session alive.
* **Role edits that ignore holders, relying on the role's level.** Rejected: a member can hold a junior role next to a senior one, so the level says nothing about who the edit reaches.

## Fitness function

* `TestArch_AuthorityWritesGoThroughTheAuthorityWriter` (`internal/architecture/authority_arch_test.go`) scans every package of `internal/identity` except the adapters, parsed and type-checked with `go/parser` + `go/types` (the route scanner's approach and its stub importer; the identity domain packages are loaded from source so the repository interfaces are real types). A write is a call that RESOLVES to `Add` or `UpdateByID` of `membership.Repository`, `role.Repository` or `permissionrequest.Repository`, whatever the receiver is called or however it was reached (alias, field, parameter, embedded wrapper). It enforces exactly: (1) outside `internal/identity/app/command` nothing writes, except the one pinned seeding of a new tenant's default roles (`seed.ApplyDefaultRoles`); (2) inside the command package each write has one native home (membership `UpdateByID` in `authorityWriter.updateMember`, role `UpdateByID` in `roleWriter.updateRole`, request `UpdateByID` in `authorityWriter.decideRequest`) and every other write is a pinned exception with its reason, asserted EXACTLY (a stale pin fails); (3) the writer entries `locked`, `updateMember` and `updateRole` are found by object (methods of `authorityWriter` / `roleWriter`), so a function that is merely NAMED `locked` is not one, and a locked pin must sit inside a function literal handed to an entry; (4) `decideRequest` is only called inside such a literal; (5) a function that adds a membership never also assigns it roles or overrides. What it does NOT prove: that a decision in a pinned or native function is the right one; the policy tables, the command tests and the attack suites do that.
* The scan also flags: a write method used as a METHOD VALUE (any selection, not only a call); an interface other than a domain `Repository` that declares `Add` or `UpdateByID` over `*membership.Membership`, `*role.Role` or `*permissionrequest.Request` (a structurally identical consumer-side interface); an authority repository, or a struct holding one, passed to a function of a faked package (type errors are swallowed there, so no selection is recorded: one pinned exception, `seed.ApplyDefaultRoles`); and any type error that names an identity-domain type.
* **What the test cannot see**: reflection; an `updateMember` closure that never calls the policy (it runs under the lock and the fresh actor, but nothing here proves it decides anything: the behavioural tests do); `cmd/api` (the composition root wires repositories and is not scanned); the adapters (they implement the repositories; their own SQL is outside the scan).
* `TestAuthorityWriteScanner_FlagsEveryBypass` pins the scanner with one synthetic offender per bypass: a direct write, an aliased receiver, a parameter of the repository type, an embedded wrapper, a free function named `locked`, a method named `locked` on another type, `roles.UpdateByID` inside `locked` instead of `updateRole`, `roles.Add` outside the writer, a membership added with roles, a request decision outside `decideRequest`, `decideRequest` outside the writer, and a new package writing a membership, a role or a request; plus the writer's own homes, a read and a locked `decideRequest`, which must pass.
* The policy decision tables in `internal/identity/domain/authority` (`TestPolicy_DecisionTable`, `round5_test.go`, `round6_test.go`), the command tests in `internal/identity/app/command`, and the attack end-to-end suites in `cmd/api` (`authority_attacks_*_e2e_test.go`, `role_holders_e2e_test.go`, `stale_actor_e2e_test.go`, `impersonation_liveness_e2e_test.go`, `permission_request_*_e2e_test.go`, `operator_exemption_e2e_test.go`, and the race tests under `-count=20`).
