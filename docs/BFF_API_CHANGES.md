# What the web BFF (leadkart-web) must handle after ADRs 0068 and 0069

Companion to [ADR 0068](adr/0068-authorization-hardening.md) and [ADR 0069](adr/0069-rank-hierarchy-and-grant-authority.md); it is the one list of every API change on branch `fix/identity-authz-and-bff-security` that the BFF or the web UI has to act on. Status: as built at the end of the final fix round (after fix round 13). The contract itself is `api/openapi.yaml` (regenerate the web types from it); local setup is [docs/LOCAL_BACKEND.md](LOCAL_BACKEND.md). Codes in the `status / code` column are the `error` field of the JSON body; switch on it, never on the message (messages are fixed strings and may change).

## 1. Contract-wide rules

| Topic | Change | Status / code | What the BFF must do |
|---|---|---|---|
| Client address | The api rate-limits, locks out and bounds password work per client address. | none (config) | Send the end client's address as `X-Forwarded-For` on EVERY call to Go (a single value, overwriting anything the browser sent; `event.getClientAddress()`). Ops list the BFF's address in `LEADKART_HTTP__TRUSTED_PROXIES`. Until both hold, every user shares one bucket (the api logs a WARN and counts `leadkart.http.trusted_proxy_header_unusable`). With adapter-node set `ADDRESS_HEADER` / `XFF_DEPTH` to the number of proxies in front of the BFF, or leave both unset when none. |
| `WWW-Authenticate` | The challenge `Bearer realm="leadkart"` is sent on 401 only (round 13); a 403 or 400 no longer carries it. | 401 | Keep treating 401 + the header as "re-authenticate / refresh silently". A 403 is never a session problem. |
| Access-token life | Documented: 600 seconds (`jwt.AccessTokenTTL`). `access_token_expires_at` in the login and refresh body is authoritative. | none | Refresh before `access_token_expires_at`. |
| Rate limits | Global per-client limit (10 requests/s, burst 60) on every route; tighter per-route limits (per minute / burst): login 30 / 10, refresh 120 / 30, request-password-reset 5 / 5, reset-password 10 / 5, confirm-email-change 10 / 5, tenant registration 10 / 5; IPv6 clients also count per `/48` on those routes; change-password 5 / 5 per person. Defaults pending the owner (ADR 0069 item 34). | 429 `rate_limited` + `Retry-After` | Surface `Retry-After` on login and reset UX; back off and retry. |
| Password work is bounded | At most 16 password operations at once per api process. One client address holds 2 slots; its further operations WAIT (at most 8, first in first out) within a 2 s queue timeout instead of failing (round 13). Anonymous login and registration use at most 12 slots, so signed-in password work always finds one. | 503 `service_busy` + `Retry-After` (same answer on every login branch: it says nothing about the account) | Honour `Retry-After`; do not fan out parallel password calls per client address. Nothing was done or counted, so a retry is safe. |
| Idempotency | `X-Command-Id` is scoped per verified tenant, person, membership, session and route (and the operator's acted-on tenant). It is IGNORED (no error, nothing stored or replayed) on `/api/v1/auth/*`, anonymous requests and safe methods. | none | Do not rely on replay for login, refresh or any auth route. |
| Error shape | Errors carry `error` (stable code), `message` (fixed) and, for validation, `errors.<field>: [rule codes]`. A full-replace body that omits or nulls a required field is `400 invalid_body` with `errors.<field>: ["required"]` (nested keys dotted, for example `address.pincode`); a wrong-typed field is `errors.<field>: ["invalid_type"]`; a repeated key or content after the object is `invalid_body`. Nothing is changed on any of them. | 400 `invalid_body` | Send complete bodies for the full-replace PATCH / PUT routes; render per-field errors. |
| Generated types | `format: email` was removed from response schemas (`CapabilitiesDto.email`, `UserDto.email`, `PersonDto.email`, `SearchPersonHit.email`); `TenantDto.status` is `pending, active, suspended, pending_deletion, deleted`; `GET /openapi.yaml` serves the real `api/openapi.yaml`. `CapabilitiesDto` gained required fields (section 2). | none | Regenerate from `api/openapi.yaml`; relax any `.strict()` schema over `CapabilitiesDto`. |

## 2. Identity and sessions

| Endpoint | Change | Status / code | What the BFF must do |
|---|---|---|---|
| `GET /auth/me/capabilities` | New required fields: `effective_permissions` (what the caller can actually do; `permissions[]` holds only `tenant.admin` for owners), `rank` (int) and `tier` (`owner`, `admin`, `manager`, `team_lead`, `user`), `must_change_password` (bool) and `password_policy` (`min_length`, `max_length` (bytes, 1024), `requires_uppercase`, `requires_lowercase`, `requires_digit`, `requires_symbol`; the caller's own tenant's rules; `min_length` counts characters). Ignores `X-Tenant-Id`. Usable while a password change is pending. Old tokens read as rank 99 / user until refresh (10 min at most). | 200 | Gate the UI on `effective_permissions` and `rank`, not on `permissions[]`. Hide an action on a member whose `rank` is not strictly greater than the caller's (owners: also on owners). Show the policy on the forced-change screen. |
| every authenticated route | `must_change_password` is enforced: while the flag is set, every route except `POST /auth/change-password` and `GET /auth/me/capabilities` answers 403. No `WWW-Authenticate`. | 403 `password_change_required` | Send the member to the change-password screen; do not refresh. Login and refresh bodies and the capabilities body carry `must_change_password` (always present). |
| `POST /auth/change-password` | Policy checked before the current password is verified. Success is 204 and ends EVERY session of that person, the caller's own included: the old access token is 401 `stale_token`, the refresh token is dead. Per-person limit 5/min. Not allowed in an impersonation session. | 204; 422 `password_policy_violation`; 401 `incorrect_current_password`; 429; 503 `service_busy`; 403 `impersonation_not_allowed` | After 204 do NOT refresh: sign in again with the password just submitted (the new token is unflagged). Render `errors.new_password` rule codes. |
| `POST /auth/reset-password`, `POST /users`, `POST /tenants` | The tenant password policy binds every new password: default 8+ characters with upper, lower, digit and symbol (owner ruling 2026-11-21; it was 12; a space is not a symbol). The web reads the policy of the caller's tenant from `GET /auth/me/capabilities` `password_policy` (`min_length` is 8 for a tenant that never stored one, more where a tenant stored its own, for example 12): nothing to hard-code, and test fixtures from the old default (11 characters) may now pass; a password over 1024 bytes is `max_length`. | 422 `password_policy_violation`, `errors.{new_password\|password\|admin_password}: [min_length, max_length, requires_uppercase, requires_lowercase, requires_digit, requires_symbol]`; 503 `service_busy` | Update test fixtures and seed scripts; render the codes. A reset ends every session of the person, so sign in again afterwards. |
| `POST /auth/login` (suspended person) | A globally suspended person can no longer sign in (round 13: the ban lasted until the next login before). The answer is the one an unknown email gets (401, same body and headers, the same lockout counting, so also 423 after ten attempts). | 401 `invalid_credentials` | Nothing new to render: a suspended person sees "wrong email or password". Do not tell a user they are suspended. |
| `POST /auth/login` | Every attempt is counted atomically; the 10th failure in 15 minutes locks, for ANY address, real or not (unknown, deactivated, anonymised): 423 with `Retry-After`, even with the correct password; the attempt that crosses the threshold with a wrong password is 423; a password over 1024 bytes is 401 like a wrong one; a login that straddles a password change is 401. | 401, 423 `account_locked` + `Retry-After`, 429, 503 `service_busy` | Keep the countdown UX; never infer that an account exists from a 423. The body always has `must_change_password`. |
| `POST /auth/refresh` | A replay of a just-rotated token within 30 seconds gets the same successor (200, same refresh token) ONLY when it comes from the same client address as the call that rotated it (the `X-Forwarded-For` the BFF sends; only a keyed hash is stored) and at most 3 times; a replay from another address, or a 4th, is reuse (family revoked, 401). The window is at most 120 s (`LEADKART_REFRESH__GRACE_WINDOW`). A stale token after that revokes the family. Refused (and the family revoked) for a globally suspended person, and after a deactivation. The body always has `must_change_password`. A session ends `Refresh.AbsoluteTTL` (14 days) after its login however often it was refreshed (round 13). | 200; 401 `refresh_rejected`; 429; 401 `refresh_rejected` with `reason: "session_expired"` once the session reached its absolute lifetime | Safe to retry a refresh whose response was lost, within 30 s, FROM THE SAME CLIENT ADDRESS: send the end client's address in `X-Forwarded-For` on every refresh (the contract-wide rule above) and keep at most 3 retries; a retry after the user's network changed signs them in again. On `refresh_rejected` go to sign-in; when `reason` is `session_expired` say "your session ended, sign in again" (the only arm that names itself). Add `reason` (optional string) to the error schema. |
| `POST /auth/reset-password` (round 13) | The token is validated before the password: an expired, unknown, used or suspended-person's token answers `reset_token_invalid` whatever the password is. A live token refused for its password (422 `password_policy_violation` or `password_breached`) is counted; the 5th refusal invalidates it (the next call is `reset_token_invalid`: ask for a new link). Resetting to the current password is now accepted (`password_same_as_current` is change-password only). | 400 `reset_token_invalid`; 422 | After the 5th 422 send the person to "request a new link"; treat `reset_token_invalid` after a 422 the same way. Remove any `password_same_as_current` handling from the reset screen. |
| `POST /auth/request-password-reset` | Always answers the same; takes at least 300 ms. | 204; 429 | Set the fetch timeout well above 300 ms. The dev mailer delivers nothing (docs/LOCAL_BACKEND.md). |
| any authenticated route, old token | After a password change or reset the old access token is dead at once on every instance when the api's cache is reachable, otherwise within 30 seconds (the api evicts the cached security stamp after the commit). The same happens to a person's token after any authority change (section 4) and to an impersonation token whose session ended or expired. | 401 `stale_token` + `WWW-Authenticate` | After an authority change: refresh silently; the new token carries the new rank and permissions. After a password change or reset: sign in again. After an impersonation session ends: fall back to the operator's own tokens (do not refresh the scoped token). |
| `GET /tenants?slug=`, `GET /tenants/by-slug/{slug}` | Now gated: `identity.tenants.view` (owners: `tenant.admin`, own tenant only) or `platform.tenants.view`. A zero-permission member used to get their own tenant or an empty list and now gets 403. | 403 `forbidden` | Read the tenant through another source, or grant the permission. |
| `GET /tenants`, `GET /tenants/{tenantId}`, `GET /tenants/by-slug/{slug}`, `GET /platform/tenants` (`password_policy`) | A company that has never saved its security settings used to report a zero policy (`min_length: 0`, `max_failed_attempts: 0`, `lockout_minutes: 0`, no classes), which is outside the declared bounds. It now reports the default policy (8 characters, all four classes, 5 attempts, 15 minutes), the same one the capabilities endpoint and the password checks already used. The schema's shape did not change. | 200 | No client change required: the API now always returns an in-contract policy, and `PATCH /tenants/{tenantId}/settings` accepts it back unchanged (204). |
| `GET /tenants/{id}`, `GET /users`, `GET /roles`, audit feed | Need `*.view` permissions; ordinary members (for example a Sales Executive) no longer see the tenant directory. Self-service `GET` and `PATCH /users/{own membership}` still work for everyone. | 403 `forbidden` | Hide the screens without the permission. |
| `GET /search` | Deleted tenants are no longer returned. Categories need their own permission (`persons`: `platform.users.view`, `tenants`: `platform.tenants.view`); with no `include` the authorised subset is returned. | 403 `search_category_forbidden` for an explicitly requested category the caller may not see | Request only categories the operator may see. |
| `POST /auth/login` (company not active) | Owner ruling 2026-11-21: "If a Company is not Active no one can login from that org." Only an ACTIVE company's members sign in. A member whose company is not active gets a distinct answer, but only AFTER the password was verified: a wrong password or an unknown email is still the ordinary 401 (same body and headers, same lockout counting), so the codes reveal nothing to a stranger. SUSPENDED company: `tenant_suspended`. PENDING or marked for deletion (`pending_deletion`) company: `tenant_not_active`. A DELETED company, and a member with no usable membership, stay 401 `invalid_credentials`. Reactivating, restoring or (for pending) activating the company restores sign-in with the same password. | 403 `tenant_suspended`; 403 `tenant_not_active` | Show "your company's account is suspended; contact support" on `tenant_suspended` and "your company is not active; contact support" on `tenant_not_active`. Do not treat either as a wrong password and do not retry. |
| `POST /auth/refresh` (company not active) | A refresh token of a member of a suspended company is refused and its family is revoked (`tenant_suspended`); the same for a company that is pending or marked for deletion (`tenant_not_active`). Suspending a company or marking it for deletion also revokes every live family of its members (worker subscriber), so the session ends at the next refresh. An access token already issued stays valid until its own expiry (600 s at most). A deleted company's members are refused without a reason. A reactivated or restored company does not bring the revoked session back: the member signs in again. | 401 `refresh_rejected` with `reason: tenant_suspended` or `reason: tenant_not_active` | Clear the session cookies and send the member to sign-in with the "company suspended" / "company not active" message. Operators acting into the non-active tenant are unaffected (their session belongs to the platform tenant). |
| `POST /auth/refresh` (idle timeout) | A session now ends when it is IDLE: each refresh token lives `Refresh.SlidingTTL` (default 24 hours: the owner's ruling of 2026-11-21, "a session unused for 24 hours ends"; it was 2 hours) from its issue, never past the absolute lifetime, and every successful rotation renews it (a grace replay does not). The first refresh after the token ran out ends the session and revokes the family (`idle_timeout`). The web refreshes whenever its 10-minute access token runs out, so an open and used session never idles; a tab parked for a day does. The absolute maximum stays 14 days. | 401 `refresh_rejected` with `reason: session_expired` (the same as the 14-day absolute end) | Treat like the absolute end: "your session ended, sign in again". Do not retry. |
| `reason` on `refresh_rejected` | The body carries `reason` ONLY for these: `session_expired` (absolute lifetime or idle timeout), `tenant_suspended` and `tenant_not_active`. Every other refusal (unknown, revoked, reuse, deleted company) has none and must stay indistinguishable. | 401 | Switch on `reason` when present; otherwise "sign in again". |
| `DELETE /auth/sessions/{familyId}` | Traced to the handler (the earlier review suspected a 404 where the spec said an idempotent 204): the CALLER'S OWN session is 204, and revoking it again is 204 as well; an id that does not exist and another person's session are both 404 `session_not_found` with identical bodies (no session-id enumeration). The spec and this row now say exactly that. | 204; 404 `session_not_found`; 400 `invalid_family_id`; 403 in an impersonation session | A 404 on a session the UI listed means it was already removed: refresh the list. |
| `DELETE /auth/sessions` (`except_current`) | The flag is honoured (it was ignored: "sign out other devices" also signed out this one). The access token now carries a `family_id` claim, the session it was minted for (login sets it, every refresh keeps it); `except_current: true` keeps that session and revokes the rest, and `revoked_count` counts only the sessions ended (never the kept one). Without the flag nothing changes: every session, this one included. A token without the claim (minted before it existed) cannot say which session to keep: nothing is revoked. A body that is present but not valid JSON is refused instead of read as "revoke everything". The BFF never reads the claim; it only sends the flag. | 200; 409 `current_session_unknown` (refresh the token and retry once); 400 `invalid_body` | Send `{"except_current": true}` for "Sign out other devices" and "Sign out everywhere" without it; on 409 refresh silently and retry. |
| `POST /auth/change-password`, `POST /auth/request-email-change`, email-change confirm (deactivated person) | These three ask the same predicate as login (`Person.MaySignIn`), so a deactivated person is refused exactly like an anonymised or globally suspended one. | the existing refusal of each (401 `incorrect_current_password`; email change rejected) | Nothing new to render. |

## 3. Tenant scope, registration and impersonation

| Endpoint | Change | Status / code | What the BFF must do |
|---|---|---|---|
| `X-Tenant-Id` (header, identity routes) | Honoured for platform operators only (slug-anchored, holding `platform.tenants.view`, or super users); everyone else's header is ignored. Reads and the pinned writable set (create user, profile, deactivate, reactivate, role and override and manager changes, anonymise, role create, update, delete, permissions, parent) work in the scoped tenant; any other write under a foreign scope is refused. A write into a suspended or pending-deletion tenant is refused (reads are allowed). The BFF is the only writer of this header (from the `lk_op_tenant` cookie). | 400 `invalid_tenant_scope`; 404 `tenant_scope_not_found`; 400 `tenant_scope_conflict` (header differs from `/tenants/{id}` in the path; path-tenant routes never need the header); 403 `tenant_scope_forbidden` (caller may not act across tenants); 403 `tenant_scope_read_only`; 403 `tenant_scope_not_supported` (permission requests, lead purchase); 409 `tenant_not_active` | Never forward a browser-supplied value. | `POST /tenants` | Operator-only: a platform operator token with `platform.tenants.create`. Own rate limit. The first admin is flagged `must_change_password`. | `PATCH /tenants/{id}/{profile,statutory,admin-contact,settings,display-preferences}` | Full replace: every field required (`settings.password_policy` needs min_length, require_*, max_failed_attempts, lockout_minutes; `admin-contact` needs phone and the whole address). `max_failed_attempts` (3 to 50) and `lockout_minutes` (0 to 1440) are accepted and returned but NOT ENFORCED: the platform lockout is fixed (10 failures in 15 minutes); they are `deprecated` in OpenAPI. A tenant may set a policy weaker than the default (`min_length` down to 8, any subset of the classes). | 400 `invalid_body` | Send every field, but HIDE `max_failed_attempts` and `lockout_minutes` in the settings screen (send the values you read back; do not present them as working controls). |
| `DELETE /platform/tenants/{tenantId}` | A tenant that still has members, roles or other dependents is refused; nothing changes. | 409 `tenant_has_dependents` (was 500) | Show the message; the purge is a follow-up. |
| `POST /platform/persons/{personId}/anonymise`, `POST /users/{userId}/anonymise` | A JSON body `{"reason":"<text>"}` is REQUIRED (no personal data in it). 409 when it would leave a tenant without its only active owner, or when the person's memberships kept changing (retry). | 400 `invalid_body` (`errors.reason: ["required"]`); 422 `person_invalid` (blank); 409 `last_owner_protected`, 409 `person_memberships_changing`; 204 | Collect a reason. |
| platform person mutations (profile, global-suspend, lift-global-suspension, anonymise) | Refused on the caller's own person. | 403 `self_modification_forbidden` | Hide the action on self. |
| impersonation routes (session create, list, end) | Authorised by the new platform-reserved permission `platform.impersonation.manage`, NOT `platform.tenants.manage`; the capabilities permission list shows it. | 403 `forbidden` without it | Guard the impersonation UI on that permission. |
| `POST` and `GET /platform/impersonation/sessions`; `GET /auth/me/capabilities` under an impersonation token | Every impersonation session representation carries `tenant_display_name`, the acted-in company's CURRENT display name (a rename shows on the next read; empty only if the tenant row is gone). The create response and every item of the list carry it. `capabilities` carries `impersonation: {session_id, tenant_display_name}` ONLY for an impersonation session's own token (absent for every other token): the one read a reloading page, or a tab whose session another tab replaced, has. An impersonation token sees only its own session (the list route stays refused to it: 403 `impersonation_not_allowed`); an operator lists only their own sessions, as before. | 201 / 200 with the new field | Read the banner name from the session (create response, or `capabilities.impersonation` after a reload / in another tab) and stop keeping it in memory; fall back to the generic wording only when the name is empty. |
| names, titles and reasons a person types: `POST /tenants` (`legal_name`, `display_name`, `admin_first_name`, `admin_last_name`), `PATCH /tenants/{id}/profile` (`legal_name`, `display_name`), `POST /tenants/{id}/suspend` and `/mark-for-deletion` (`reason`), `POST /users` (`first_name`, `last_name`), `PATCH /users/{id}/profile` (`designation`, `department`, `status_message`), `POST /users/{id}/deactivate` and `/anonymise` (`reason`), `PATCH /platform/persons/{id}/profile` (`first_name`, `last_name`), `POST /platform/persons/{id}/global-suspend` and `/anonymise` (`reason`), `POST` and `PATCH /roles` (`name`), `PATCH /roles/{id}/parent` (`reason`), `POST /platform/impersonation/sessions` (`reason`), `POST /permission-requests` (`reason`) and `/approve`, `/deny` (`decision_reason`) | A value holding a control character (U+0000-U+001F, U+007F-U+009F: CR, LF and TAB included), a Unicode direction control (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069) or an invisible or line-breaking character (U+00AD, U+034F, U+115F, U+1160, U+180E, U+200B, U+2028, U+2029, U+2060-U+2064, U+3164, U+FEFF, U+FFA0, U+FFF9-U+FFFC, the TAG block U+E0000-U+E007F) is refused, nothing is written. No field is multi-line. Letters of every script, combining marks, emoji, the no-break space and the ideographic space are accepted. The zero-width joiner and non-joiner (U+200D, U+200C) are accepted INSIDE a word (the character before and after each is a letter or a combining mark: Hindi, Marathi, Bengali, Persian, Urdu spellings) and refused at the start or end, next to a space, digit, punctuation, symbol or another joiner, so a joined emoji sequence (a family emoji) is refused. Nothing else is loosened: a ZWJ after another virama (Devanagari, Tamil, ...) at a word end, and U+200C anywhere outside a word, stay refused. A full-replace body (`PATCH /tenants/{id}/profile`, `/users/{id}/profile`, `/platform/persons/{id}/profile`, role rename) that re-sends a stored value UNCHANGED is accepted even if that old value holds such a character: only a changed value is checked. Existing data is not rewritten and reads never fail. | 422 with the route's code (`tenant_invalid`, `person_invalid`, `user_invalid`, `role_invalid`, `role_hierarchy_invalid_reason`, `impersonation_invalid`, `permission_request_invalid`; a registration's company names answer `tenant_invalid`, its admin's names `person_invalid` under `admin_first_name` / `admin_last_name`) and `errors.<field>: ["invalid_characters"]`; the message never echoes the value | Mark the named field with the new code `invalid_characters`; strip refused control, direction and invisible characters before sending (pasted text often carries them), but do NOT strip U+200C / U+200D that sit inside a word: removing them changes the spelling of a real name. Send the text as typed and let the server decide. Do not rely on the old 500 for a bad registration name. |
