# What the web BFF (leadkart-web) must handle after ADRs 0068 and 0069

Companion to [ADR 0068](adr/0068-authorization-hardening.md) and [ADR 0069](adr/0069-rank-hierarchy-and-grant-authority.md); it is the one list of every API change on branch `fix/identity-authz-and-bff-security` that the BFF or the web UI has to act on. Status: as built at the end of fix round 13. The contract itself is `api/openapi.yaml` (regenerate the web types from it); local setup is [docs/LOCAL_BACKEND.md](LOCAL_BACKEND.md). Codes in the `status / code` column are the `error` field of the JSON body; switch on it, never on the message (messages are fixed strings and may change).

## 1. Contract-wide rules

| Topic | Change | Status / code | What the BFF must do |
|---|---|---|---|
| Client address | The api rate-limits, locks out and bounds password work per client address. | none (config) | Send the end client's address as `X-Forwarded-For` on EVERY call to Go (a single value, overwriting anything the browser sent; `event.getClientAddress()`). Ops list the BFF's address in `LEADKART_HTTP__TRUSTED_PROXIES`. Until both hold, every user shares one bucket (the api logs a WARN and counts `leadkart.http.trusted_proxy_header_unusable`). With adapter-node set `ADDRESS_HEADER` / `XFF_DEPTH` to the number of proxies in front of the BFF, or leave both unset when none. |
| `WWW-Authenticate` | The challenge `Bearer realm="leadkart"` is sent on 401 only (round 13); a 403 or 400 no longer carries it. | 401 | Keep treating 401 + the header as "re-authenticate / refresh silently". A 403 is never a session problem. |
| Access-token life | Documented: 600 seconds (`jwt.AccessTokenTTL`). `access_token_expires_at` in the login and refresh body is authoritative. | none | Refresh before `access_token_expires_at`. |
| Rate limits | Global per-client limit (10 requests/s, burst 60) on every route; tighter per-route limits (per minute / burst): login 30 / 10, refresh 120 / 30, request-password-reset 5 / 5, reset-password 10 / 5, confirm-email-change 10 / 5, tenant registration 10 / 5; IPv6 clients also count per `/48` on those routes; change-password 5 / 5 per person. Defaults pending the owner (ADR 0069 item 34). | 429 `rate_limited` + `Retry-After` | Surface `Retry-After` on login and reset UX; back off and retry. |
| Password work is bounded | At most 16 password operations at once per api process. One client address holds 2 slots; its further operations WAIT (at most 8, first in first out) within a 2 s queue timeout instead of failing (round 13). Anonymous login and registration use at most 12 slots, so signed-in password work always finds one. | 503 `service_busy` + `Retry-After` (same answer on every login branch: it says nothing about the account) | Honour `Retry-After`; do not fan out parallel password calls per client address. Nothing was done or counted, so a retry is safe. |
| Idempotency | `X-Command-Id` is scoped per verified tenant, person, membership, session and route (and the operator's acted-on tenant). It is IGNORED (no error, nothing stored or replayed) on `/api/v1/auth/*`, anonymous requests and safe methods. | none | Do not rely on replay for login, refresh or any auth route. |
| Error shape | Errors carry `error` (stable code), `message` (fixed) and, for validation, `errors.<field>: [rule codes]`. A full-replace body that omits or nulls a required field is `400 invalid_body` with `errors.<field>: ["required"]` (nested keys dotted, for example `address.pincode`); a wrong-typed field is `errors.<field>: ["invalid_type"]`; a repeated key or content after the object is `invalid_body`. Nothing is changed on any of them. | 400 `invalid_body` | Send complete bodies for the full-replace PATCH / PUT routes; render per-field errors. |
| Generated types | `format: email` was removed from response schemas (`CapabilitiesDto.email`, `UserDto.email`, `PersonDto.email`, `SearchPersonHit.email`); `TenantDto.status` is `pending, active, suspended, pending_deletion, deleted`; `GET /openapi.yaml` serves the real `api/openapi.yaml`. `CapabilitiesDto` gained required fields (section 2). | none | Regenerate from `api/openapi.yaml`; relax any `.strict()` schema over `CapabilitiesDto`. |

## 2. Identity and sessions

| Endpoint | Change | Status / code | What the BFF must do |
|---|---|---|---|
| `GET /auth/me/capabilities` | New required fields: `effective_permissions` (what the caller can actually do; `permissions[]` holds only `tenant.admin` for owners), `rank` (int) and `tier` (`owner`, `admin`, `manager`, `team_lead`, `user`), `must_change_password` (bool) and `password_policy` (`min_length`, `max_length` (bytes, 1024), `requires_uppercase`, `requires_lowercase`, `requires_digit`, `requires_symbol`; the caller's own tenant's rules; `min_length` counts characters). Ignores `X-Tenant-Id`. Usable while a password change is pending. Old tokens read as rank 99 / user until refresh (10 min at most). | 200 | Gate the UI on `effective_permissions` and `rank`, not on `permissions[]`. Hide an action on a member whose `rank` is not strictly greater than the caller's (owners: also on owners). Show the policy on the forced-change screen. |
| every authenticated route | `must_change_password` is enforced: while the flag is set, every route except `POST /auth/change-password` and `GET /auth/me/capabilities` answers 403. No `WWW-Authenticate`. | 403 `password_change_required` | Send the member to the change-password screen; do not refresh. Login and refresh bodies and the capabilities body carry `must_change_password` (always present). |
| `POST /auth/change-password` | Policy checked before the current password is verified. Success is 204 and ends EVERY session of that person, the caller's own included: the old access token is 401 `stale_token`, the refresh token is dead. Per-person limit 5/min. Not allowed in an impersonation session. | 204; 422 `password_policy_violation`; 401 `incorrect_current_password`; 429; 503 `service_busy`; 403 `impersonation_not_allowed` | After 204 do NOT refresh: sign in again with the password just submitted (the new token is unflagged). Render `errors.new_password` rule codes. |
| `POST /auth/reset-password`, `POST /users`, `POST /tenants` | The tenant password policy binds every new password: default 12+ characters with upper, lower, digit and symbol (a space is not a symbol); a password over 1024 bytes is `max_length`. | 422 `password_policy_violation`, `errors.{new_password\|password\|admin_password}: [min_length, max_length, requires_uppercase, requires_lowercase, requires_digit, requires_symbol]`; 503 `service_busy` | Update test fixtures and seed scripts; render the codes. A reset ends every session of the person, so sign in again afterwards. |
| `POST /auth/login` | Every attempt is counted atomically; the 10th failure in 15 minutes locks, for ANY address, real or not (unknown, deactivated, anonymised): 423 with `Retry-After`, even with the correct password; the attempt that crosses the threshold with a wrong password is 423; a password over 1024 bytes is 401 like a wrong one; a login that straddles a password change is 401. | 401, 423 `account_locked` + `Retry-After`, 429, 503 `service_busy` | Keep the countdown UX; never infer that an account exists from a 423. The body always has `must_change_password`. |
| `POST /auth/refresh` | A replay of a just-rotated token within 30 seconds gets the same successor (200, same refresh token), so retries and a second tab are safe. A stale token after that revokes the family. Refused (and the family revoked) for a globally suspended person, and after a deactivation. The body always has `must_change_password`. | 200; 401 `refresh_rejected`; 429 | Safe to retry a refresh whose response was lost, within 30 s. On `refresh_rejected` go to sign-in. |
| `POST /auth/request-password-reset` | Always answers the same; takes at least 300 ms. | 204; 429 | Set the fetch timeout well above 300 ms. The dev mailer delivers nothing (docs/LOCAL_BACKEND.md). |
| any authenticated route, old token | After a password change or reset the old access token is dead at once on every instance (the api evicts the cached security stamp after the commit). The same happens to a person's token after any authority change (section 4) and to an impersonation token whose session ended or expired. | 401 `stale_token` + `WWW-Authenticate` | After an authority change: refresh silently; the new token carries the new rank and permissions. After a password change or reset: sign in again. After an impersonation session ends: fall back to the operator's own tokens (do not refresh the scoped token). |
| `GET /tenants?slug=`, `GET /tenants/by-slug/{slug}` | Now gated: `identity.tenants.view` (owners: `tenant.admin`, own tenant only) or `platform.tenants.view`. A zero-permission member used to get their own tenant or an empty list and now gets 403. | 403 `forbidden` | Read the tenant through another source, or grant the permission. |
| `GET /tenants/{id}`, `GET /users`, `GET /roles`, audit feed | Need `*.view` permissions; ordinary members (for example a Sales Executive) no longer see the tenant directory. Self-service `GET` and `PATCH /users/{own membership}` still work for everyone. | 403 `forbidden` | Hide the screens without the permission. |
| `GET /search` | Deleted tenants are no longer returned. Categories need their own permission (`persons`: `platform.users.view`, `tenants`: `platform.tenants.view`); with no `include` the authorised subset is returned. | 403 `search_category_forbidden` for an explicitly requested category the caller may not see | Request only categories the operator may see. |

## 3. Tenant scope, registration and impersonation

| Endpoint | Change | Status / code | What the BFF must do |
|---|---|---|---|
| `X-Tenant-Id` (header, identity routes) | Honoured for platform operators only (slug-anchored, holding `platform.tenants.view`, or super users); everyone else's header is ignored. Reads and the pinned writable set (create user, profile, deactivate, reactivate, role and override and manager changes, anonymise, role create, update, delete, permissions, parent) work in the scoped tenant; any other write under a foreign scope is refused. A write into a suspended or pending-deletion tenant is refused (reads are allowed). The BFF is the only writer of this header (from the `lk_op_tenant` cookie). | 400 `invalid_tenant_scope`; 404 `tenant_scope_not_found`; 400 `tenant_scope_conflict` (header differs from `/tenants/{id}` in the path; path-tenant routes never need the header); 403 `tenant_scope_forbidden` (caller may not act across tenants); 403 `tenant_scope_read_only`; 403 `tenant_scope_not_supported` (permission requests, lead purchase); 409 `tenant_not_active` | Never forward a browser-supplied value. Show scope errors in the operator console. |
| `POST /tenants` | Operator-only: a platform operator token with `platform.tenants.create`. Own rate limit. The first admin is flagged `must_change_password`. | 401 anonymous; 403 `forbidden`; 422 `password_policy_violation` (`admin_password`); 429 | The operator console already sends a Bearer token; anonymous sign-up is gone. |
| `PATCH /tenants/{id}/{profile,statutory,admin-contact,settings,display-preferences}` | Full replace: every field required (`settings.password_policy` needs min_length, require_*, max_failed_attempts, lockout_minutes; `admin-contact` needs phone and the whole address). | 400 `invalid_body` | Send every field. |
| `DELETE /platform/tenants/{tenantId}` | A tenant that still has members, roles or other dependents is refused; nothing changes. | 409 `tenant_has_dependents` (was 500) | Show the message; the purge is a follow-up. |
| `POST /platform/persons/{personId}/anonymise`, `POST /users/{userId}/anonymise` | A JSON body `{"reason":"<text>"}` is REQUIRED (no personal data in it). 409 when it would leave a tenant without its only active owner, or when the person's memberships kept changing (retry). | 400 `invalid_body` (`errors.reason: ["required"]`); 422 `person_invalid` (blank); 409 `last_owner_protected`, 409 `person_memberships_changing`; 204 | Collect a reason. |
| platform person mutations (profile, global-suspend, lift-global-suspension, anonymise) | Refused on the caller's own person. | 403 `self_modification_forbidden` | Hide the action on self. |
| impersonation routes (session create, list, end) | Authorised by the new platform-reserved permission `platform.impersonation.manage`, NOT `platform.tenants.manage`; the capabilities permission list shows it. | 403 `forbidden` without it | Guard the impersonation UI on that permission. |
| any route, impersonation token | The scoped token acts as the target tenant's admin on tenant routes. Self-service routes (change-password, email change, sessions, `/me/activity`, permission-request submit, approve, deny, cancel), `/platform/*`, tenant register and lifecycle, search and anonymise are refused. The audience and the `act` claim must agree. The token is live only while its session is. Two tenant-plane reads under `/platform/` (`GET /platform/marketplace/leads`, `GET /platform/lead-credits/balance`) stay open to a session. | 403 `impersonation_not_allowed`; 401 `unauthenticated` (aud/act mismatch); 401 `stale_token` once the session ended | Hide those UIs during impersonation; on "stop impersonating" use the operator's own tokens. |
| `POST /users` with an impersonation token | Allowed (accepted risk, ADR 0069 item 25); the creation rows carry the operator and reason. | 201 (was 500) | none |

## 4. Authority: rank, roles, overrides, approvals

Rank is `capabilities.rank` / `tier` (0 owner, 1 to 10 admin, 11 to 20 manager, 21 to 30 team_lead, 31 to 99 user; lower is more senior). Every authority route decides on the acting member's CURRENT rank and permissions (re-read under a lock), never on the token alone. Every 403 on these routes carries a fixed `error`: switch on it.

| Endpoint | Change | Status / code | What the BFF must do |
|---|---|---|---|
| users: `POST /users/{id}/roles`, `DELETE /users/{id}/roles/{roleId}`, `PATCH /users/{id}/permission-overrides`, `POST /users/{id}/deactivate`, `POST /users/{id}/reactivate`, `PUT` and `DELETE /users/{id}/manager`, `PATCH /users/{id}/profile` (another member) | The caller must strictly outrank the target (owners may act on owners). Self-target is refused for everyone but super users. Conferring or removing a permission the caller does not hold (or holds only until a date), or `tenant.admin` for a non-owner, is refused; a role above the caller's rank is refused; only a super user assigns a super-admin role. | 403 `insufficient_rank`; 403 `self_modification_forbidden`; 403 `grant_exceeds_authority`; 403 `forbidden` (the acting member no longer exists or is inactive) | Hide the action on a member the caller does not outrank. |
| role assign / revoke, deactivate, anonymise, global-suspend | An unknown or deleted role is 404 `role_not_found`. The last active owner cannot be removed; `tenant.admin` cannot be revoked from an owner. A member whose roles cannot be loaded blocks the change. Reactivating a person who is active in another company is refused. | 404 `role_not_found`; 409 `last_owner_protected`; 409 `owner_protected`; 409 `member_roles_inconsistent`; 409 `person_active_elsewhere` (was 500) | Show the message. |
| `PUT /users/{id}/manager` | Authority is checked before eligibility. | 403 `insufficient_rank` / `self_modification_forbidden`, then 422 `manager_not_eligible` (manager inactive, foreign, not more senior, missing or a cycle) | |
| `PATCH /users/{id}/permission-overrides` | A name in both lists is refused (was 500); a repeated name in one list counts once; lifting a name from `revoked` needs the Admin tier; an unchanged save changes nothing and does not end the member's token. | 422 `validation_failed` (`errors.revoked`); 403 `grant_exceeds_authority`; 204 | |
| operator under `X-Tenant-Id` (role assign / revoke of Company Owner or any role carrying `tenant.admin`, conferring or removing `tenant.admin`, deactivating or reactivating an owner) | Needs `platform.tenants.ownership`. | 403 `ownership_authority_required` | Day-to-day operator actions are unchanged. |
| roles: `POST /roles`, `PATCH /roles/{id}`, `PUT /roles/{id}/permissions`, `POST /roles/{id}/permissions/grant\|revoke`, `PATCH /roles/{id}/parent`, `DELETE /roles/{id}` | `hierarchy_level` is REQUIRED on create (1 to 99; 0 is refused) and must be below the caller's rank. Re-level: not above or equal to the caller's rank; refused if it would newly break a reporting line. The caller must hold every permission added AND removed. Holders (active or not) must be junior to the caller; a caller who holds the role cannot edit it (owners may). System-default roles cannot change. Delete is refused while an ACTIVE member holds the role (`errors.active_holders`), checked after rank. `PATCH /roles/{id}` with neither `name` nor `hierarchy_level` is refused. `PUT .../permissions` needs the `permissions` key (`{}` or `null` is refused; `[]` clears). `PATCH .../parent` needs the `parent_role_id` key (`null` or `""` clears). Each edit ends every active holder's old access token. | 400 `invalid_body`; 422 `role_invalid`; 403 `insufficient_rank` / `self_modification_forbidden` / `grant_exceeds_authority`; 422 `role_level_breaks_reporting`; 422 `role_parent_not_eligible` (a foreign parent was `role_hierarchy_cross_tenant`); 409 `role_system_default`; 409 `role_in_use`; 409 `role_name_taken`; 404 `role_not_found` | Disable the editors the caller may not use; show the holder count on `role_in_use`. The seeded roles moved (Company Owner 0, Administrator and Office Administrator 10, Senior Manager 15, department managers 20, Team Lead 30, executives 50). |
| `POST /permission-requests` | Needs `identity.meta.request_permission_elevation` (every seeded non-owner role has it). A non-requestable name is refused. | 403 `forbidden`; 403 `impersonation_not_allowed`; 422 `permission_not_requestable` | |
| `GET /permission-requests?role=approver` | Lists the pending requests the caller may DENY; every item has `can_approve`. A caller who can decide nothing gets an empty page; a manager below Admin sees only their reports'. A page can be shorter than `page_size` while `has_more` is true: keep following `next_cursor`. `role=requester` items carry no `can_approve`. | 200 | Enable Approve only when `can_approve` is true, Deny always. |
| `GET /permission-requests/{id}` | Visible to the requester and to anyone who may deny it, decided on the fresh actor. | 404 `permission_request_not_found` for everyone else | |
| `POST /permission-requests/{id}/approve` and `/deny` | A caller who may not decide gets 404 (no 403 `not_approver`; that code no longer exists). Authority errors: approving a permission the approver does not hold, or lifting a revoked name below the Admin tier; the requester themself; an impersonation session. Approval grants exactly the stored permission for the stored duration, capped at the approver's own time-bound grant. State: not pending; requester inactive (approve only). An Administrator-tier approver may approve `identity.users.{create,update,deactivate,reactivate,unlock}` without holding them. | 404 `permission_request_not_found`; 403 `grant_exceeds_authority` / `insufficient_rank` / `self_modification_forbidden` / `impersonation_not_allowed`; 409 `permission_request_not_pending`; 409 `permission_request_requester_inactive`; 409 `member_roles_inconsistent`; 422 `permission_not_requestable` | An approval ends the requester's old token (refresh silently). |
| `POST /permission-requests/{id}/cancel` | Serialised with approve and deny. | existing statuses | |
| stamp rotation | Role assigned or revoked, overrides replaced, deactivate, reactivate, an approval (the requester), a role definition edit (every holder) end the TARGET's old access token. A change that leaves the target as it was ends nothing. Deactivation also ends the session (refresh refused). Manager changes, profile edits, denials and cancellations rotate nothing. | 401 `stale_token` + `WWW-Authenticate` on the target's next request | Refresh silently; the new token carries the new rank and permissions. |

## 5. Not decided yet (do not build around these)

The pending-owner list in [ADR 0069](adr/0069-rank-hierarchy-and-grant-authority.md#pending-owner-confirmation) holds every controller or implementer default (rate-limit numbers, the Argon2 numbers of 2 running and 8 waiting, the 30 s refresh grace, the default password policy, whether a session may create members, ...). Only the three rulings in "Decided by the owner" are decisions; the rest may change by configuration or a later ADR.
